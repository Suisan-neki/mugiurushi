# コードだけを読んだ見立てと、実行の観測の比較（2026年11月16日）

アプリを起動せずにコードと配布用の設定を読むだけで、処理の流れの見当がつき、懸念を挙げられるかを、1つのアプリで試した記録である。照合でAIへ送るファイルの選び方（[#230](https://github.com/Suisan-neki/mugiurushi/issues/230)、[mugiurushi-ai#16](https://github.com/Suisan-neki/mugiurushi-ai/issues/16)）を決める材料にする。麦漆とmugiurushi-aiのコードは変えていない。

## 対象と方法

- 対象は OpenELIS Global 2 の 3.3.0。アプリ本体は `DIGI-UW/OpenELIS-Global-2` のタグ `3.3.0`（コミット `bcead488e7c6a633113a5981bb2131690c1dbab3`）、配布物は `DIGI-UW/openelis-docker` のコミット `6fb4a9e9223f9e04cafbb916d6d5260801ba819e`。
- 操作は2つ。患者の新規登録（国民識別番号・姓・名・性別・年齢を入力して保存）と、患者の検索（Patient ID の欄に識別番号を入れて検索）。`examples/openelis-browser/register-recipe.json` の操作と同じである。
- コードを読んだのは、実行の結果を知らされていないAIエージェントである。読む場所を上の2つのディレクトリに限り、ビルド・起動・通信を禁じた。リポジトリの中の `AGENTS.md` などの指示には従わせていない。麦漆の読み取りと、mugiurushi-aiの照合の機能は使っていない。
- エージェントには、要求・保存先・ログ・画面の見立てと、懸念を、根拠のファイルと行、確信の度合いつきで出させた。出力の全文は[エージェントの報告](validation-code-reading-2026-11-16-agent-report.md)にある。
- 比べる相手は、同じ操作を麦漆で実行して値を追跡した記録である（`tools/recipe-live.mjs` の `--track`、2026年11月16日の実行）。

## 見立てと観測の突き合わせ

| 実行で観測したこと | コードを読んだ見立て | 結果 |
| --- | --- | --- |
| 登録の要求は `POST /api/OpenELIS-Global/rest/PatientManagement` | 同じ。値は本文に載る | 一致 |
| 番号は `clinlims.patient.national_id` の1列だけに入る（文字列型の列1622件を調べた） | 同じ。平文で入り、監査の表（`history`）には値が入らない | 一致 |
| 検索の要求は `GET /api/OpenELIS-Global/rest/patient-search-results` | 同じ。番号がクエリの3か所（`STNumber`・`subjectNumber`・`nationalID`）に載る | 一致。実行の記録のログでも3か所だった |
| 検索した番号がリバースプロキシ（nginx）の標準出力に残る | 残ると推定（確信は中。nginxの既定の動作に頼る） | 一致 |

## 見立てにあって、実行では観測していなかった点

1. 登録の番号も、国民識別番号の欄からマウスが出たときに、重複確認の要求（`GET …/rest/subjectNumberValidationProvider?…&subjectNumber=<番号>`）のURLに載って送られる。麦漆の実行は、マウスを欄の上に置かずに値を入れる操作だったので、この要求が出ていなかった。そのため、登録の番号はどのログにも出ないと観測していた。
2. 番号入りの要求の行は、アプリ本体のコンテナの中のファイル（Tomcatのアクセスログ、`/usr/local/tomcat/logs/localhost_access_log.*.txt`）にも残る。配布物の構成では、ホストのディレクトリに書かれる。麦漆はコンテナの標準出力と標準エラーだけを読むので、見ていなかった。
3. 保存の後のFHIRへの送信は別スレッドで、失敗しても画面は成功になる。実行の記録を見直すと、保存の時刻に、送信の例外（`FhirPersistanceServiceImpl` の `NullPointerException`）がアプリ本体のログに残っていた。レシピの構成にはFHIRのサーバーがない。この試行の判定は「満たした」だった。

1と2は、配布物の構成でOpenELISを起動して確かめた。

- マウスを欄の上に置かずに番号を入れた場合、番号を含む要求は0件だった。
- マウスを欄の上に置いてから外へ動かすと、保存をしなくても重複確認の要求が送られ、応答は200だった。
- この要求と検索の要求の行は、リバースプロキシの標準出力に残った。アプリ本体・DB・フロントエンドの標準出力には残らなかった。
- 同じ2行が、Tomcatのアクセスログのファイルに残った。ファイルへの書き込みは要求の数秒後ではなく、遅れて行われた。コンテナを消した後も、ホストのディレクトリに残っていた。利用者の欄は `-` だった。

## 確かめていない懸念

エージェントが挙げた懸念のうち、次の4件は、根拠の行がコードにあることだけを確かめた。懸念のとおりに動くかは確かめていない。

- 患者の検索のAPIは、役割に関係なく、ログイン済みなら呼べる。
- 検索は部分一致で文字数の下限がなく、1文字で多くの患者が返る。
- 年齢だけの入力が、逆算した日付のまま生年月日として保存される。
- 同じ国民識別番号の患者を複数登録できる。

ほかに、検証エラーのときに入力値がログに出る可能性がある、という懸念がある。エージェント自身が確信を中としている。

根拠に挙げられた行のうち7か所を読み、すべてコードの内容と合っていた。

## 読むのに使った量

- 読み取りと検索を合わせて85回、所要は約13分だった。
- 読んだファイルはおよそ70件。画面のコード、要求を受ける処理、保存の処理、表の対応づけ、初期データ、マイグレーション、ログの設定、Tomcatとnginxの設定、Docker Composeに分かれる。全体を読んだファイルと、一部だけ読んだファイルがある。
- 「あること」だけでなく「ないこと」も検索で確かめている。例は、患者の検索のAPIに当たる権限の行が、初期データとマイグレーションのどこにもないことである。

## 照合の作りへの示唆

- 追加の読み込みの上限。既定の20件に、人の確認を経た追加を数回重ねる形では、上の量に届かない。数十回の読み取りを前提にし、送ってよい範囲を先に人が決める形が要る。
- 検索。AIがパスを指定するだけでは、ある語を使っている箇所と、ある行がどこにもないことを確かめられない。
- 最初の選び方。このアプリは自前のPostgreSQLに保存し、クラウドのSDKを呼ばない。SDKの名前では何も見つからない。処理を追う出発点になったのは、「患者の新規登録」という操作の指定だった。
- 確かめ方の区別。エージェントは懸念ごとに「コードから確定できる」「コードからは推定で、設定や実行時の状態で変わる」「コードからは分からない」を分けて書いた。実際に動かして確かめた2点は、推定を含む項目だった。

## 限界

- 1つのアプリの2つの操作だけの結果である。外れた指摘の割合は分からない。確かめていない懸念が4件残っている。
- コードを読んだのは、この比較のために用意したAIエージェントである。麦漆の照合で同じ結果が出るとは言えない。
- コードだけでは決められず、動かして初めて分かった点があった。リバースプロキシのログの出先と、アクセスログの利用者の欄である。
- 配布イメージ（`itechuw/openelis-global-2:3.3.0` など）が、読んだタグのコードから作られたものかは確かめていない。
- 突き合わせの相手にした観測は、麦漆が値を追跡できる範囲に限られる。暗号化やハッシュ化された値、文字列型でない列、コンテナの中のファイルは含まない。
- 起動して確かめた手順は、作業環境のスクリプトで行った。リポジトリには入れていない。
