# 相談と試験の対応づけの調査と実装（2026年11月2日）

対象はmainの81f48ec（PR #202のマージ後）。依頼文（本人、2026年11月2日）の懸念1〜5を、コードとテストに照らして確認した。本書は、コードを読んで分かったこと、CIで実行して確認したこと、未確認のことを分けて書く。

## 調査で分かったこと

### 実装されていること（コードから確認）

- 対話の整理案（`src/system_diagram/dialogue.rs`の`Record`）には、検証課題・主体・操作・期待・関連箇所・根拠・未確認事項・検証案（`test_plan`: 操作・期待・観測の文）・報告された結果・改善案がある。根拠の行は渡した抜粋と照合し、範囲外の参照を含む返答は保存しない。参照行の存在は説明の正しさの証明ではない。
- `ui/app.js`の`handoffDialogue`は、期待（人が編集した文）を確認項目の`text`に、未確認事項を未回答の質問に、最初の検証済み参照を`source`にして`add_check`する。変更前は`test_plan`は引き継がず、対話の保存記録にだけ残っていた。
- `ui/workbench.js`は`GET /api/v1/browser-recipes`の同梱レシピ（`src/browser_recipes.rs`。OpenEMRのSOAP通常時・DB停止・患者A/B）を選び、`configure_observation`で`eel.trial`を設定し、`POST /api/v1/execute`で実行する。レシピのセレクター・DB構造・操作はOpenEMR固有で、`examples/openemr-browser/`にある。操作・HTTP応答・DB読み出し・判定は`src/browser.rs`と`src/trial.rs`の汎用部分が担う。
- `src/trial.rs`の`assess`は、判定条件ごとの結果（期待どおり・期待と異なる・観測できていない）をまとめ、同じ範囲で食い違えば判定せず、失敗があれば「満たさない」、観測の欠落があれば「判定できない」、すべて通れば「満たす」とする。DBを読めなかったことは`NotObserved`、正常に読んで試験値が含まれないことは`Fail`で区別する（`src/browser.rs`の`evaluate`、既存テスト`absent_and_failed_reads_do_not_pass_negative_expectations`）。
- 通信の記録（`src/container.rs`の`TrafficSummary`）は接続元・接続先・件数・バイト数の集計で、通信の中身は含まない。試験用ネットワークの外への送信先の特定や分散トレースは実装にない。

### 誤判定につながる可能性があったこと（変更前の処理）

`src/workspace.rs`の`view`は、確認項目の`verdict`を最新の適用できる試行の判定だけから決め、`verification_passed = verdict == Satisfied`としていた。事例全体の`verification_passed`はその全件の論理積で、`Decide { action: Release }`はそれだけを見て許可していた。確認項目の文と試行の判定条件の関係はどこにも記録・照合されていない。

したがって「意図しない外部にも診療データが送信されないか」という確認項目にSOAP保存のレシピを結び付けて全条件が通ると、確認項目は「満たす」、事例は「全条件の検証を通過」となり、「採用する」を記録できた。PR #202で追加された画面の注意文は表示だけで、APIの判定・保存データ・採用判断は変わっていなかった。

この挙動は`tests/coverage.rs`の`passing_storage_trial_does_not_answer_an_unrelated_concern`で、外部送信に関する確認項目へ保存の試験を取り込む形で再現し、変更後は試行の判定が「満たす」のままでも確認項目は未通過で「採用する」を記録できないことを確認した。

### CI run 41367490398で行われたこと

ワークフローは一時的な`temporary-openemr-check.yml`で、`npm run test:browser-handoff -- --live`を実行した。`tools/browser-handoff-smoke.mjs`は、確認項目を`add_check`で固定の文（「SOAPを保存して開き直し、4項目の内容をDBと照合できる」）として直接登録し、画面から同梱レシピを選んで実OpenEMRを起動し、保存・再表示・DB照合を行った。AIとの対話、Dify、整理案からの引き継ぎは含まれない。固定レシピによる接続確認であり、AIを含む通し試験ではない。

### 実装はあるが実環境・実AIでは未確認のこと

- Dify・OpenAI互換APIの実接続と回答品質。`tools/dialogue-smoke.mjs`は合成のAI応答で、形式検査・根拠照合・引き継ぎだけを確認する。
- 参照したOpenEMRのGitコミットと、実行したコンテナイメージのコードの一致。
- 本番環境での保存先、外部への送信の有無。

## 変更したこと

- `src/coverage.rs`: 観測の種類の一覧（判定に使える種類＝`trial::CheckMethod`と対象プログラムの観測・外部の報告、記録のみ＝通信の集計、推定＝コードの読取、未対応＝通信の中身・分散トレース・外部の送信先・本番環境）。確認項目の「確かめたい部分」（`Aspect`: 文・出所・観測の種類・対応づける判定条件ID）と、適用できる最新の試行の判定条件ID・観測方法との照合。文章の一致では判断しない。
- `src/workspace.rs`: `Check.aspects`、`set_aspects`操作、`CheckView.coverage`。`verdict`は試行の判定のまま、`verification_passed`は試行の判定が満たされ、かつ登録した部分をすべて観測した場合だけ真。未登録・未対応・未観測・期待と異なる部分が残る確認項目では「採用する」を記録できない。対応づけの登録は条件の版を変えない（試行の解釈であり、既存の試行は適用できるまま照合し直す）。
- `GET /api/v1/observation-kinds`、確認資料（`src/review_report.rs`）への部分ごとの状態の記載。
- `ui/workbench.js`: 実行前の確認画面で、人が部分ごとに観測の種類とこの試験の判定条件を選んで登録する。結果画面に試験の判定と部分ごとの状態を分けて表示する。
- `ui/app.js`: AIの検証案を部分の下書きとして引き継ぐ。観測の種類と判定条件は人が選ぶまで未定で、試験が通っても観測済みにならない。

## 妥当性の確認（合成データ、CI）

`tests/coverage.rs`（架空のメモ記録アプリをPython 3で実行）:

| ケース | 確認した結果 |
| --- | --- |
| 1. 相談と試験が対応し観測が得られる | 保存先の読み出しと読み直しに対応づけた部分が観測され、確認項目が通過し「採用する」を記録できる |
| 2. 保存の相談に外部送信の部分を結び付ける | 試行は「満たす」でも、外部の送信先・通信の中身は未対応、通信の集計は記録のみとなり、未通過。「採用する」は拒否 |
| 3. 条件が不明 | 未回答の質問があれば試行が通っても判定しない。観測の種類が未定の部分は「未定」 |
| 4. 観測方法がない | 未対応の種類を選んだ部分は「基盤が観測できない」として残る |
| 5. 読めない／正常に読んで無い | 読み出しを止めた試行は「観測できていない」、表示は成功と言うが保存先に無い試行は「期待と異なる」 |
| 6. 表示とDBの食い違い | 受付の表示は観測、保存先は期待と異なる。確認項目は未通過 |
| 7. 試験・版の変更後 | 読み直しを外した試験では前の試行の読み直しを「最新の試行に判定条件がない」とし、版を変えると「適用できる試行がない」になる |

画面試験（合成の読取記録、実OpenEMRなし）: `tools/browser-handoff-smoke.mjs`で対応づけの登録と未対応の表示、`tools/result-observations-smoke.mjs`で結果画面の表、`tools/dialogue-smoke.mjs`で対話からの下書きの引き継ぎを確認する。

## レビュー（2026年11月2日、コミット347c784）への対応

本人のレビュー（2026年11月2日）で3点の指摘を受けた。

1. 判定条件の識別子と観測方法だけで照合すると、手動設定の`c1`が別の内容（患者Aの表示→患者Bの表示）に変わっても前の対応づけが有効になる。→ 対応づけに判定条件の内容の指紋を持たせ（`TrialLink`）、登録時にサーバーが`definition`から計算する。識別子が同じで内容が違えば`definition_changed`とし、人が確認し直す。`tests/coverage.rs`の`same_check_id_with_a_different_definition_requires_a_new_link`で、同じID・同じ観測方法で期待または範囲だけを変えた試験に前の対応づけが適用されないことを確認した。
2. 画面で対応づけを変えても保存ボタンの状態が更新されず、未保存のまま試験を始められる。→ 入力・チェックの変更ごとに保存状態を更新し、未保存の変更があるうちは「試験を始める」を拒否する。`tools/browser-handoff-smoke.mjs`で確認した。
3. 期待する動作が同じ再検証では、続けた対話の検証案・未確認事項が確認項目に引き継がれない。→ 同じ期待でも、増えた未確認事項を質問に、増えた検証案を部分の下書きに追加する（既存の部分と人の対応づけは上書きしない）。`tools/dialogue-smoke.mjs`で確認した。

## 再レビュー（2026年11月3日、コミットae31418）への対応

1. 別の部分を保存すると、変わった判定条件にも現在の内容で対応づけ直されていた。→ 画面は新しく選んだ・選び直した対応づけだけ`definition`を送り、それ以外は保存済みの指紋と説明を送る。サーバーは`definition`のない対応づけの指紋を更新しない。変わった対応づけは画面で明示し、「現在の内容で対応づけ直す」を人が押すまで前の指紋を保つ（この試験には適用されない）。
2. 指紋が判定条件だけを対象にしていた。→ 判定条件が属する試験設定（起動・引数・入力・故障・保存先・読み直し・待つプロセス・コンテナ・HTTP操作・ブラウザの準備・操作・DBの問い合わせ先）を指紋に含めた。固定版（コミット）は含めず、試行の適用可否で扱う。

追加した確認: `tests/coverage.rs`の`changing_only_the_operated_target_requires_relinking_and_saving_other_parts_keeps_old_links`（判定条件は同じで操作対象の引数だけを変えた試験に前の対応づけを適用せず、別の部分を保存しても指紋が変わらず、選び直すと観測済みになる）、`src/coverage.rs`の単体テスト（引数の違いで指紋が変わり、コミットと待機上限の違いでは変わらない）、`tools/browser-handoff-smoke.mjs`（同じ判定条件のままDB停止の試験へ変えると変更を表示し、別の部分の保存で指紋が変わらず、対応づけ直しで変わる）。

## 今回も達成できていないこと

- AIの検証案を実行可能な試験へ自動で変換することは行っていない。案は下書きとして残り、人が観測の種類と判定条件を選ぶ。
- 外部への送信の有無、通信の中身、分散トレース、本番環境の保存は観測できない。未対応として明示するにとどまる。
- 実AI・Dify・実OpenEMRを含む通し実行は、この作業環境（Rustツールチェーンとcrates.ioに接続できない）では実行していない。Rustとブラウザ試験はPRのCIで実行した。
