### 誤判定につながる可能性があったこと（変更前の処理）

`src/workspace.rs`の`view`は、確認項目の`verdict`を最新の適用できる試行の判定だけから決め、`verification_passed = verdict == Satisfied`としていた。事例全体の`verification_passed`はその全件の論理積で、`Decide { action: Release }`はそれだけを見て許可していた。確認項目の文と試行の判定条件の関係はどこにも記録・照合されていない。

したがって「意図しない外部にも診療データが送信されないか」という確認項目にSOAP保存のレシピを結び付けて全条件が通ると、確認項目は「満たす」、事例は「全条件の検証を通過」となり、「採用する」を記録できた。PR #202で追加された画面の注意文は表示だけで、APIの判定・保存データ・採用判断は変わっていなかった。

この挙動は`tests/coverage.rs`の`passing_storage_trial_does_not_answer_an_unrelated_concern`で、外部送信に関する確認項目へ保存の試験を取り込む形で再現し、変更後は試行の判定が「満たす」のままでも確認項目は未通過で「採用する」を記録できないことを確認した。

### 1. 試験設定の変更内容を比較できるか

変更前に対応づけ（`TrialLink`）に保存していたのは、識別子・指紋・一行の説明だけだった。説明が含むのは範囲・観測方法・期待・文・対象・故障・起動対象・引数で、次の変更は指紋が変わっても内容を示せなかった。

- 判定条件の`relation`、入力（`input`）、起動のしかた、保存先、読み直し、Pythonの読み込み先、待つプロセス、試験用コンテナ（イメージ・環境変数・ボリューム・コマンド・準備の待機）、HTTP操作
- ブラウザの準備・操作の手順と順序、観測するHTTP応答、DBの問い合わせ先（表・列・照合値）、直接要求する読み出し、拒否の観測

変更後の動作:

- 対応づけるとき（`set_aspects`で`definition`を送ったとき）、麦漆は指紋と説明に加えて、その時点の判定条件（`basis.check`）と試験設定（`Check.link_settings`。同じ設定は1件にまとめ、参照されなくなった記録は残さない）を保存する。試験設定は指紋の対象と同じ項目で、コンテナの環境変数の値だけ「（記録しない値）」に置き換える。
- `POST /api/v1/link-changes`（読み取り専用）と、結果の`coverage.aspects[].link_changes`は、対応づけた時点と現在（または試行）の設定を値ごとに比べ、区分（判定条件・ブラウザ操作・DBの問い合わせ先・故障の条件など）、場所、前後の値を返す。識別子のある配列は識別子で対応させ、順序の違いも示す。
- 比較できないことは推測で補わず`uncomparable`に示す。環境変数の値だけが変わった場合は「記録した項目には違いがない。記録しない値が変わった可能性がある」と示す。この機能より前の対応づけは、同じ指紋で実行した試行の記録から時点の設定を示し（判定には使わない）、それもなければ「保存されていない。何が変わったかは示せない」と示す。試験案を使わない試行（観測名と対象）は指紋だけで照合し、変更内容は示せないと示す。
- 実行前の確認画面は、変わった対応づけごとに区分別の件数と前後の値を示してから「違いを確認した。現在の内容で対応づけ直す」を出す。結果画面も同じ一覧を示す。確認資料（HTML・埋め込みJSON）には変わった区分の名前だけを載せ、値と時点の設定は載せない。
- 別の部分を保存しても、内容を送らない対応づけは、保存済みの同じ識別子・指紋の対応づけの説明と時点の記録を保つ。変更前は利用者が送った説明（label）でそのまま上書きできたため、保存済みの説明を使うように直した。時点の記録（`basis`）は利用者から受け取らない。
- 新しい確認項目（`add_check`）に対応づけを含めて送ると拒否する。変更前は指紋・説明の作成を経ずに対応づけを持ち込めた。画面と同梱ツールは送っていない。

秘密情報・実データの扱い（現行の確認）:

- ブラウザのログイン情報はレシピでは`Input::Secret{key}`で、値はレシピ外の`EEL_BROWSER_SECRETS_FILE`から読む。対応づけの記録にも比較にも値は入らない。
- コンテナの環境変数には試験用DBのパスワードなど（同梱レシピでは`eel-root-trial`など試験専用の値）が平文で入る。これは従来から実行記録（`evidence.execution.recipe`）に全文保存されており、今回は変えていない。対応づけの記録と比較では値を伏せる。
- ブラウザの入力値（`Input::Literal`）と`input`は試験の操作定義として記録・比較する（実行記録にも同じものがある）。同梱レシピでは`{{test_value}}`の雛形と架空の文字列で、実データは含まない。利用者が実データをレシピに書いた場合に検出する仕組みはない。

互換性: `basis`と`link_settings`がない保存データはそのまま読める（既定値）。新しい保存データを変更前の版では読めない（`deny_unknown_fields`）。指紋の計算は変えていないため、保存済みの指紋は引き続き一致する。`POST /api/v1/trial-fingerprints`は画面からの利用がなくなったため削除した（このPRで追加したもので、main・リリースには含まれていない）。

### 2. 指紋の対象と限界

| 項目 | 指紋 | 変わった場合の扱い |
| --- | --- | --- |
| 判定条件（範囲・観測方法・期待・文・対象・relation） | 含む | 対応づけを適用しない（`definition_changed`） |
| 実行方式・起動のしかた・起動対象・引数・入力・故障・保存先・読み直し・Python・待つプロセス・コンテナ（イメージのダイジェスト・環境変数・コマンドなど）・HTTP操作・ブラウザの設定 | 含む | 同上 |
| 固定版（リポジトリ・コミット・パス・行） | 含まない | 確認項目の参照と異なる試行は適用できない（`evidence_invalidated_by`）。同じ対応づけは新しい版の試行にも使う（対応づけは「この判定条件がこの部分に答える」という宣言で、コードの版に依らない設計） |
| 判定の観測名・対象（`criterion`） | 含まない | 確認項目の設定と異なる試行は適用できない |
| 試験の待機上限（`timeout_ms`） | 含まない | 上限に達した観測は「観測できていない」になり、期待どおりにはならない |
| 復旧後の読み直し（`trial.recovery`） | 含まない | 判定に使う読み出しの後に行い、結果は判定条件の結果に入らない（`execution.rs`で読み出しの後に`recover_and_compare`） |
| 同じ試験のほかの判定条件 | 含まない | 部分の状態はその判定条件の結果だけで決める。確認項目の通過には試行全体の判定が「満たす」ことも必要 |
| レシピ外の値（秘密値ファイルの中身、事前準備した環境、Playwright・Chromiumの版、試行ごとの試験値） | 含まない | 実行記録に残る範囲で確認する。対応づけの照合では扱わない |

一貫性: `definition_changed`の部分は観測済みにならず、`coverage.status`が`covered`でないため`verification_passed`は偽になり、「採用する」は拒否される。確認画面は「この試験では確かめない部分」に含め、結果画面と確認資料は状態と変わった区分を示す（`tests/coverage.rs`の`changed_trial_shows_what_changed_and_keeps_the_recorded_basis_until_relinked`ほか）。比較の取得に失敗した場合、確認画面は「比べられませんでした。変わった対応づけがあっても表示されません」と示す。判定は画面の比較ではなく、実行記録から計算した指紋で行う。

実行前に確認した設定と実行した設定: 画面は確認画面の比較と実行要求に同じ`buildRecipe`と同じフォームの値を使う。サーバーは受け取った試験設定を変えずに実行し、実行記録に保存する（`review_execution.rs`の`start`から`execute_with_dependencies`へ移すだけ）。差は固定版・確認項目ID・観測名だけで、いずれも指紋の対象外かつ適用可否で扱う。仮に画面と実行がずれても、照合は実行記録の設定から計算した指紋で行うため、対応づけは適用されない（観測済みにならない）。
