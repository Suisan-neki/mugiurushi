# コードから出た懸念の試験を、OpenELISで動かした結果（2026年11月19日）

照合の作り直し（[#230](https://github.com/Suisan-neki/mugiurushi/issues/230)）で、コードをたどって出た懸念から、実際のモデルで試験の案を作った（[記録](validation-concern-plan-live-2026-11-19.md)）。その案のうち、環境の設定を変えずに観測できると見込んだ3件（c-2、c-6、c-7）を、OpenELIS Global 2 の 3.3.0 で動かした記録である。案を書いたモデルの判断ではなく、動かして観測した結果で、懸念が起きるかを確かめた。

## 対象と方法

| 項目 | 値 |
| --- | --- |
| 対象 | `DIGI-UW/OpenELIS-Global-2` のタグ `3.3.0`（コミット `bcead488`）のイメージ。起動の設定は `examples/openelis-browser/register-recipe.json`（配布物 `DIGI-UW/openelis-docker` のコミット `6fb4a9e9`、5つのイメージをダイジェストで固定） |
| 麦漆 | `main` の `abad64f` に、2つのレシピを足したもの |
| 患者 | 架空の氏名（Yamada Taro、Suzuki Hanako）と、試行ごとに作る架空の国民識別番号 |

進め方は2段である。

1. 探索：配布物の構成（`docker compose`）で OpenELIS を起動し、Playwright と psql で画面とDBを直接調べた。案に「要確認」とあった画面の経路と設定の変え方を決め、懸念が起きるかを先に確かめた。
2. 麦漆での判定：探索で決めた手順を麦漆のレシピに書き、麦漆の実行器で1回ずつ動かした。判定は麦漆の観測だけで決まる。

この環境の都合で、次の3点を、その実行に限って置き換えた。レシピのファイルは変えていない。

- 入口のnginx：カーネルにIPv6がないので、`--command` で `listen [::]` の行を外して起動した（[例の説明](../examples/openelis-browser/README.md)の「IPv6を持たないホストで動かす場合」と同じ手当て）。
- ブラウザ：レシピは Chromium 151.0.7922.34 を指定しているが、この環境にあるのは 153.0.8010.12 だけだった。版の指定をその版に書き換えた写しで実行し、`EEL_BROWSER_EXECUTABLE` で実行ファイルを渡した。
- 利用者：root では Chromium のサンドボックスが動かないので、一般の利用者で実行した。

## 結果

| 懸念 | 探索で観測したこと | 麦漆の判定 |
| --- | --- | --- |
| c-6 重複の拒否の文に、既存の患者の氏名と生年月日が入る | 起きた。拒否の応答は `400 {"error":"National ID SYN3658374 already belongs to patient Yamada, Taro, born 18/11/1986"}`。同じ文が、アプリの標準出力のERRORの行（`LogEvent.logError(new BindException(...))`）にも出た | 満たしていない。拒否される：期待どおり。応答の本文に `Yamada` が無い：期待と異なる。アプリのログに `Yamada` が無い：期待と異なる（141秒） |
| c-2 国民識別番号が、重複確認の要求のURLを通じてアクセスログに残る | 起きた。欄からマウスが離れると `GET /rest/subjectNumberValidationProvider?...&subjectNumber=<番号>` が送られ、入口のnginxの標準出力とTomcatのアクセスログのファイルの両方に、番号を含む要求の行が残った | 満たしていない。要求が送られた：期待どおり。入口のログに試験値が無い：期待と異なる。アプリの標準出力に試験値が無い：期待どおり（134秒） |
| c-7 緊急連絡先を空欄にしても、空の連絡先の行ができる | 起きた。空欄で登録した患者に、氏名・電話・メールがすべて空の `patient_contact` の行と `person` の行ができた。この探索用のDBで以前の試行に登録した架空の患者10人すべてに、同じ空の行があった | レシピで書けなかった（下記） |

麦漆の判定は、どれも探索で直接観測したことと一致した。c-2の「アプリの標準出力に試験値が無い」が期待どおりなのは、Tomcatのアクセスログが標準出力ではなくコンテナ内のファイルに書かれるためである。麦漆のログの判定条件は、そのファイルを見ていない。

## 試験の案について分かったこと

- c-6の案の最初の手順「重複を禁止する設定 `ALLOW_DUPLICATE_NATIONAL_IDS` を false にする（設定方法は要確認）」は、必要な手順だった。アプリのコードの既定値は false だが、配布物の初期データ（liquibase の `2.3.x.x/national_id_config.xml`）が true にしている。設定を変えないと重複が許され、拒否の文は作られない。設定は、管理画面の Admin › Patient Entry Configuration で変えられた。
- c-6の案の合格の条件（応答とログに氏名と生年月日が含まれない）は、そのまま判定条件にできた。ログの転送先は、この環境にないので確かめていない。
- c-2の案は、要求のきっかけを「欄からマウスを離す」と書いていた。コード（`onMouseOut`）のとおりで、文字を入れるだけでは要求は送られなかった。案の2つ目の合格の条件（ログが無い場合は、設定で記録が無効であることを確かめる）は、ログがあったので使わなかった。
- 3件とも、画面のURLと選択子は案では「要確認」だった。探索で決めた。

## 麦漆の基盤で書けなかったこと

c-7は、「空欄で登録した患者に、空の連絡先の行が結び付いていない」ことを確かめたい。麦漆のDBの読み出しは、表の1つの列が試験値に一致する行だけを読む。`patient_contact` には試験値（国民識別番号）の列がなく、患者の行のID（`patient.id`）でたどる必要がある。読み出した行の値で次の読み出しを絞る指定がないので、書けなかった。

同じ理由で、「行が1件だけ」のような件数の条件も書けない。c-6では、2人目が保存されていないことを、応答が `400` であることで代わりに確かめた。

## 確認できたこと・できていないこと

- 確認できた：コードから出た懸念3件は、3.3.0 で実際に起きた。c-6とc-2は、麦漆のレシピで「満たしていない」と判定でき、判定は直接の観測と一致した。案の「要確認」の手順は、探索で埋められた。
- 確認していない：
  - c-7を麦漆で判定すること。
  - ログの転送先、Tomcatのアクセスログのファイル（麦漆の観測の外）。
  - 固定した版のブラウザ（151.0.7922.34）と、IPv6のあるホストでの実行。
  - 各レシピの2回以上の実行。判定が毎回同じかは分からない。
  - これらの懸念を不具合とみるかどうか。麦漆は観測と判定を示すだけで、運用上の可否は決めない。

## 追記（2026年11月20日）：c-7を麦漆で判定した

DBの読み出しを前に読んだ行の値でつなげるようにし（`match_from`）、行が無いことを判定する条件（`zero`）を足した。c-7のレシピ（`examples/openelis-browser/empty-emergency-contact-recipe.json`）を、上と同じ置き換えで1回実行した。判定は「満たしていない」（183秒）。

| 判定条件 | 結果 |
| --- | --- |
| 患者が保存される（`status=200`） | 期待どおり |
| 国民識別番号の患者の行がある | 期待どおり（1行） |
| その患者の `id` で読んだ `patient_contact` の行が無い | 期待と異なる（1行） |

読み出しは3段でつながった。患者の行（`id` 2）から `patient_contact` の行（`person_id` 3）、`person` の行（`id` 3）へたどり、その `person` の行の氏名・電話・メールはすべて空だった。探索で直接見たことと一致する。
