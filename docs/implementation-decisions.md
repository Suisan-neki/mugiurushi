# 今回の実装で選んだこと

## 2026年11月17日 往復で使ったトークン数を残す

照合の作り直し（#230）の段階4（実際のモデルでの試行）の準備。費用を記録から出せるようにした。

- 往復ごとに、AIエージェントが返したモデル名と、入力・キャッシュから読んだ入力・出力のトークン数を記録に残す。キャッシュから読んだ入力は単価が違うので分ける（mugiurushi-ai の側で、APIの `input_tokens_details.cached_tokens` を返すようにした）。
- 記録と結果に、トークン数の合計を残す。送った往復の数（`calls`）と、トークン数を受け取れた往復の数（`reported`）を分ける。応答の前後で失敗してトークン数を受け取れなかった往復があるか、どれかの往復で数が分からない場合は、合計を `null` にする。分からない分を除いた数や0を合計として見せると、費用を少なく見積もるためである。
- 画面の結果にも、使ったトークン数を示す。金額には直さない。単価はモデルと処理の種類で変わり、麦漆は単価を持たないためである。

確かめたこと：偽のAIエージェントで、往復ごとの数と合計が記録と結果に残ること、数が分からない往復と、トークン数を受け取れずに失敗した往復があると合計が `null` になること、画面に示すこと。分からない数を0と数える版と、結果に合計を残さない版で、試験が失敗することを確かめた。

## 2026年11月16日 コードをたどって懸念を出す画面

照合の作り直し（#230）の段階3のうち、画面の部分。照合の画面（`/flow`）の1つ目の段に「コードをたどって懸念を出す（任意）」を足した。

- 範囲は、画面の入力から組み立てずに麦漆が返したものをそのまま示し、そのSHA-256も示す。了承するのは、麦漆がSHA-256を計算した範囲そのものである。送らないパスは、既定の指定と人が足した指定を合わせた全体を示す。
- 了承の欄に印を付けるまで「この範囲で始める」は押せない。範囲を確かめ直すと、前の了承は消える。
- 結果は事例の記録（`/api/v1/flow`）に、対象の操作、足した送らないパス、往復の上限と一緒に残す。開き直したときは記録から出し、送り直さない。結果は今の記録の物に書き足し、物を差し替えない。往復の途中でほかの段へ移ると、その段の操作（回答、試験の案）が今の記録の物を書き換えるためである。
- 根拠の行は、固定したコミットのGitHubの該当行へのリンクにした。人が根拠をその場で読めるようにするためである。
- 根拠の種類の表記は「このリポジトリのコードと設定」と「リポジトリの外にある製品の既定の動き」にした。どちらも推定であり、「確定」とは書かない。

確かめたこと：偽のAIエージェントの応答で、照合の画面の試験（`npm run test:flow`）に場面を足した。対象の操作がなければ送らないこと、範囲の確認で送った入力、示した送らないパスと上限と範囲のSHA-256、了承の前は始められないこと、了承でSHA-256を添えること、結果の表示、根拠の行のリンク、開き直しで送り直さず記録から出すこと、往復の途中で照合とヒアリングの段へ移っても回答と試験の案と往復の結果がすべて記録に残ること。了承の前に押せないようにする処理、操作の確認、SHA-256の添付、結果の表示、記録からの表示、送らないパスの空行の除去を外すと、それぞれ試験が失敗することを確かめた。

確かめていないこと：実際のAIエージェントとモデルでの往復と、往復にかかる時間（段階4）。往復の途中の進み具合は出ない。懸念を選んで試験の案へつなぐことは、まだしていない。

受け渡しの形は `tests/contract/agent/investigate-first-round.json` と `investigate-second-round.json` に固定し、AIエージェントの側が同じファイルを入力にして試験する。

## 2026年11月16日 照合のために、固定したコミットを手元に取得し、検索と範囲の読み取りに答える

照合の作り直し（#230、mugiurushi-ai#16）の段階1。AIエージェントが「この語で検索したい」「このファイルのこの範囲を読みたい」と求めたときに、麦漆が固定したコミットから答える部品（`src/code_tree.rs`）を作った。往復の実行、範囲の了承、画面は段階3で作る。この段階では、AIエージェントとはつないでいない。

これまでは、ファイルの中身を必要なときに1件ずつGitHubから取り寄せていた（`src/reader/github.rs`）。リポジトリ全体を検索する手段がなかった。

- 固定したコミットだけを `git fetch --depth 1` で取得する。作業ツリーは作らず、bare のリポジトリから読む。対象のファイルを手元に展開しないので、シンボリックリンクや実行の権限が手元に現れない。取得したものは、次に同じコミットを開くときに使い回す。
- 検索は `git grep -F`。語を正規表現として扱わないので、AIエージェントが渡す語で、検索が遅くなる形を作れない。
- 送らないパスの既定は、秘密の値を持つことが多い種類のファイル（`.env`、鍵ファイル、`.npmrc` など）だけにした。名前に「secret」を含むコードのファイルは、処理を読むために必要なので含めない。利用者は指定を足せる。
- 送るかどうかは、このモジュールの照合で決める。gitの除外の指定（pathspec）にも渡すが、それは、送らないファイルの行で検索の結果の上限を使い切らないためである。gitの指定と照合の書き方が少しでもずれた場合に、送らないファイルが出ることがないようにした。
- 読めるのは通常のファイルだけにした。シンボリックリンク、サブモジュール、NULを含むファイル、UTF-8でないファイル、1MiBを超えるファイルは読まない。検索でも、これらのファイルの行は返さず、当たった件数の上限にも数えない。gitの `-I` はファイルの先頭しかバイナリかどうかを見ず、UTF-8かどうかも見ないので、当たったファイルの内容を麦漆が確かめる。
- 読み取りの本文は、範囲の先頭の行から行番号と1行ずつ対応させる。範囲が空行から始まっても、その空行を落とさない。
- 返す量の上限：読み取りは1回400行・4万文字まで、検索の結果は50件まで（1件の行は300文字まで、前後1行つき）。上限で打ち切ったときは、結果にそう示す。
- 取得の通信には、利用者のgitの設定（プロキシなど）を使う。手元のリポジトリの中の操作では、利用者のgitの設定とフックを使わない。取得のURLの方式は https だけを許す（試験では file）。

確かめたこと：架空のリポジトリの単体試験7件。送らないファイルの行が検索の結果に出ないことは、gitの除外の指定を渡さない検索でも確かめ、照合を外すとその試験が失敗することを確かめた。GitHubの公開リポジトリでの試験（`tests/code_tree.rs`、`--ignored`）で、OpenELIS Global 2 の 3.3.0（ファイル10,762件）を取得と一覧に約10秒、検索に約0.9秒で扱えた。コード読みの比較（[記録](validation-code-reading-2026-11-16.md)）で根拠になった画面のコードの行へ、検索と読み取りでたどり着けた。

確かめていないこと：非公開のリポジトリ（読み取り自体に対応していない）。取得の容量の上限（今はファイルの件数の上限だけ）。同じコミットを同時に取得した場合の動きは、置き場所を移すときの競合を扱うコードを書いたが、試験していない。

## 2026年11月16日 画面の記録と通信の記録にも、切り捨てたヘッダーの名前を残す

- 文書の応答（`DocumentResponse`）とやり取り（`ExchangeRecord`）に `headers_truncated` を足した。切り捨てていないときは書かないので、変更前の記録も読める。
- 基盤は、名前が記録したヘッダーを1回ずつだけ指すことを検査する。記録していないヘッダーを指す名前を受け取ると、何が欠けているのかを読み手が誤るためである。
- AIエージェントは、画面の記録の知らない項目を受け取らずに拒否する（422）。AIエージェントの側で項目を受け取れるようにしてから、この変更を使う。受け渡しの固定ファイル（`tests/contract/agent/`）に、切り捨てたヘッダーを含む例を入れた。

## 2026年11月16日 終了の合図を受けたら、試験用の資源を回収してから終わる

実行器（`mugiurushi` の実行ファイル）は、SIGTERMやSIGINTを受けると、その場で終わっていた。試行のために起動した子のプロセス、コンテナ、ネットワーク、ボリュームは残った。通常の回収が、値の破棄（`Drop`）の処理に頼っていて、合図で終わるプロセスでは破棄の処理が動かないためである。PR 225 のレビューで、確認用スクリプトが上限の時間で実行器を止めたときに資源が残ると指摘され、スクリプトの側で回収していた。実行器を止めるのはこのスクリプトだけではない（端末のCtrl+C、CIの時間切れ、画面のサーバーの停止）ので、実行器の側で回収する。

**動き。**

- SIGTERMまたはSIGINTを受けると、動かしている資源を回収し、行ったことを標準エラーへ1行で書いて、終了コード143（SIGTERM）または130（SIGINT）で終わる。残った資源があれば、同じ行に書く。資源を控えていないとき（試行を動かしていないとき）は、何も書かずに同じ終了コードで終わる。
- 回収するのは、このプロセスが作って控えている資源だけである。専用のプロセスグループで起動した子（対象のプログラム、ブラウザの操作器とブラウザ）、試行のラベルを持つコンテナ・ネットワーク・ボリューム、固定環境の実行で名前を付けて作ったコンテナ、実行中の `docker` コマンドである。ほかの試行や、麦漆が作っていない資源には触れない。
- 子のプロセスグループには、先にSIGTERMを送り、1.5秒後にSIGKILLを送る。ブラウザの操作器が、ブラウザを閉じてから終われるようにするためである。
- 回収の途中で2回目の合図を受けても、回収を続ける。もう一度送れば止められることを標準エラーへ書く。3回目の合図を受けたら、回収を待たずに終わる。Dockerが応答しない場合に、止める手段を残すためである。この場合、資源は残りうる。
- 2回目で終わる作りにしなかったのは、ジョブを取り消す仕組みに、合図を続けて送るものがあるためである。GitHub Actionsのランナーは、取り消しのときにSIGINTを送り、7.5秒後にSIGTERMを送り、さらに2.5秒後にプロセスを強制終了する（[Workflow cancellation](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation)）。2回目で終わると、回収が7.5秒で終わらない試行では、資源が残る。OpenELISの試行の回収には7秒かかった。
- 確かめたこと：OpenELISの試行へSIGINTを送り、7.5秒後にまだ動いていればSIGTERMを送る手順で実行した。実行器は7.5秒以内に終了コード130で終わり、コンテナ9、ネットワーク2、ボリューム5、Chromiumのプロセス11はすべて0になった。この回では2回目の合図は送られなかった。2回目の合図で回収が続くことと、3回目で終わることは、Dockerを使わない試験（`tests/shutdown.rs`）で確かめている。
- 中継として動く場合（`relay`）は、資源を持たないので、合図の扱いを変えない。

**設計上の判断。**

- 合図を受ける関数の中では、パイプへ1バイト書くことだけを行う。回収は、パイプを読む別のスレッドが行う。合図の途中で呼んでよい操作は限られていて、`docker` の実行や排他の取得はできないためである。
- 合図の扱いには、すでに依存している `libc` の `sigaction` を使った。依存を増やしていない。
- 回収は、試行を動かしているスレッドとは別のスレッドで動く。そのため、回収の後に試行の側が資源を作ると、その資源が残る。資源を作る操作（子の起動、`docker create`・`docker run`・`docker network create`・`docker volume create`）は、1か所（`shutdown::creating`）を通す。回収は、作っている途中の操作が終わるのを待ってから始める。回収を始めた後の操作は、何も作らずにエラーを返す。
- 確かめたこと：この待ち合わせを外すと、コンテナを作っている途中に合図を送った試験で、実行器が終わった後にコンテナが1つ残った。`docker run` のコマンドは、実行器が終わった後も動き続けてコンテナを作るためである。待ち合わせを入れた版では、同じ試験を3回くり返して残りは0だった。
- 確かめたこと：OpenELIS Global 2 のレシピ（`examples/openelis-browser/register-recipe.json`）を実行し、ブラウザの操作が始まった後に実行器へSIGTERMを送った。合図の直前には、コンテナ9、ネットワーク2、ボリューム5、Chromiumのプロセス11があった。実行器は7秒後に終了コード143で終わり、どれも0になった。
- 回収が子のプロセスを止めると、試行の処理は「子が終わった」と見て先へ進み、通常の終了コードで終わることがある。合図で終わったことが終了コードで分かるように、処理の終わりで回収の終了を待つ。
- 確認用スクリプト（`tools/recipe-live.mjs`）の、上限の時間で止めた後の回収は残した。実行器が回収した後に残りがないことを確かめ、残っていれば消す。OpenELISのレシピを上限60秒で実行したところ、実行器が止められた後、スクリプトの側で消す資源は0件で、残りも0だった。上限で止めた場合、実行器が標準エラーへ書いた報告はスクリプトへ届かない。Node.jsが、止めるときに子の出力の受け口を閉じるためである。

**レビューの指摘で直した2点。**

- Dockerに尋ねられなかった場合を、残りがない場合と分けて報告する。直す前は、一覧の取得に失敗すると空の一覧として扱い、「残った資源はない」と書いていた。残りを確かめられなかった資源は、試行やコンテナの名前と、失敗の内容を書く。
- 固定環境の実行で作ったコンテナは、作ったときと同じ接続先で消す。固定環境の実行は、親の環境変数を `docker` へ渡さない。直す前の回収は、親の `DOCKER_HOST` を渡す別の呼び出しを使っていたので、この変数を設定した環境では、別のデーモンへ削除を求めていた。

## 2026年11月16日 操作の記録を実在のアプリで試し、道具の不具合3点を直す

操作を記録して手順を書き出す道具（`tools/browser-recorder.mjs`）を、OpenELIS Global 2 のログインから患者登録・検索までの操作で試した。これまでは架空の画面でしか試していなかった。記録した手順は、最初は再実行で最後まで進まなかった。原因は道具の側に3点あり、どれも対象によらない不具合だった。結果は `examples/openelis-browser/README.md` にある。

**1. ラベルを押した操作を、隠れた欄へのクリックとして記録していた。**

- 確かめたこと：OpenELISの性別の選択は、欄そのものを見えなくして、ラベルを押させるラジオボタンである。ラベルを押すと、ブラウザは結び付いた欄へもクリックを送る。道具は、この欄へのクリックだけを記録していた。再実行では、その欄を押せずに時間切れになった。
- チェックボックスやラジオボタンに結び付いたラベルを押した操作は、ラベルへのクリックとして記録する。続けて届く欄へのクリックは数えない。欄そのものを押した操作は、これまでどおり欄へのクリックとして記録する。
- ラベルは、結び付いた欄のID（`label[for="…"]`）で指す。ラベルの文字で指す方法は採らなかった。同じ文字を含む別のラベル（Male と Female）と区別できない場合があるためである。

**2. 人が応答を待ったことが、記録に残らなかった。**

- 確かめたこと：保存のボタンを押した直後に次のボタンを押すと、保存の完了で画面が切り替わり、次の欄が消えた。人は保存が終わるのを見てから次の操作をするが、記録には待ったことが残っていなかった。
- クリックの後に対象が送った書き込みの要求（GET以外）の応答が、次の操作の前に届いた場合は、その要求を応答の観測先として書き出し、クリックの手順に `wait_response` を付ける。次の操作の前に応答が届かなかった要求には付けない。人は待っていないためである。
- 対象にするメソッドは、POST、PUT、PATCH、DELETEである。GETは、設定の取得や定期の問い合わせが多く、どれを人が待ったのかを決められない。HEADやOPTIONSは、レシピの応答の観測先が受け付けないので、待ち合わせにするとレシピの検査が拒否する。読み込みの完了を待つ必要がある画面では、画面の表示を読む手順が待ち合わせになる。

**3. 一意かどうかを、クリックで変わった後の画面で調べていた。**

- 確かめたこと：ログインのボタンは、押す前の画面では「Login」という名前のボタンとして1つだけ見つかる。押すと画面が移る。道具は、クリックが届いてから一意かどうかを調べていたので、役割と名前では見つからず、位置で指すCSSになっていた。
- 要素を押し始めた時点（`pointerdown`）で特徴を届け、その時点の画面で調べる。続くクリックが同じ要素なら、その結果を使う。人が押している時間（押し始めてから離すまで）の間に調べ終わることを前提にしている。押している時間がごく短い場合と、キーボードで押した場合は、これまでどおりクリックの時点で調べる。

**道具の規則の版を2にした。** 同じ操作から作る手順が変わるためである。

**候補の取り込みを、対象によらない確認用スクリプトに足した（`tools/recipe-live.mjs` の `--adopt`）。** これまでは、OpenEMR用のスクリプト（`tools/openemr-tracking-live.mjs`）の中にだけあった。そちらは変えていない。判定条件は、候補が作る種類だけを置き換え、画面の表示の条件は残す。

**レビューの指摘で直した、候補の取り込みの3点。** 取り込みの処理を `tools/recipe-adopt.mjs` に分け、コンテナを起動しない試験（`npm run test:recipe-adopt`）を足した。

- 値の割り当て（値の追跡と、手順ごとの値）を、候補のもとになった試行のままにする。手順ごとの値で作った候補は、読み出しと判定条件に手順ごとの値を持つ。割り当てを外すと、入力した値と一致しない。
- 応答の観測先とDBの読み出し先を省略したレシピにも取り込める。
- 残した判定条件が参照するDBの読み出し先を残す。DBの行どうしの対応の条件は候補が作らないので残すが、読み出し先をすべて候補に置き換えると、参照先がなくなる。

**実装していないこと。**

- 画面の表示を読む手順と、その判定条件を作ること。何を確かめるかは、人が選ぶ。
- 記録のときの「人の操作」は、台本（`tools/openelis-recorder-live.mjs`）が要素の位置へ入力を送って作った。人が画面を表示するブラウザで操作した記録は、取っていない。
- 待った応答のパスが実行のたびに変わる場合の扱い。

## 2026年11月16日 コンテナへファイルを置く指定、別名、終了を待つコンテナを足す

OpenELIS Global 2 のレシピで、レシピの側の回り道のまま残していた3つを、基盤で表せるようにした。3つとも Docker Compose が持っている機能にあたり、対象ごとの処理は足していない。必要だと分かった根拠は、OpenELISの1件である。

**1. 固定したコミットのファイルを、コンテナの中へ置く（`files`）。**

- 出所は、レシピが固定しているリポジトリとコミットの中のファイルに限った。同じレシピなら、誰が実行しても同じ内容が置かれる。レシピに内容を直接書く指定と、ディレクトリごとの指定は足していない。OpenELIS 3.3.0 には要らなかった。
- ブラウザの試験の固定版は、参照するファイル1つだけを写していた。`files` に書いたファイルも固定版に含める。固定コミットにないファイルは、何も起動する前に拒否する。
- コンテナを作成し、ファイルを置いてから起動する。起動の後に置くと、対象が読む時点に間に合わない。
- ファイルは、ファイルの見出しだけを入れたtarを `docker cp` へ渡して置く。ディレクトリの見出しを入れないので、ない親のディレクトリは作られ、既にあるディレクトリ（`/tmp` など）の権限と所有者は変わらない。ホストのディレクトリをそのまま写す方法は、既にあるディレクトリの権限を書き換えるので採らなかった。
- 所有者はroot、権限は0644（実行できるファイルは0755）、時刻は0に固定した。同じ入力から同じ内容を作るためである。root以外で動く対象が、0644のファイルを読めない置き場所に置かれた場合は確かめていない。
- 上限は、1コンテナ16件、1件1MiBにした。固定版の上限（1ファイル4MiB）より小さい。設定ファイルを想定した値で、根拠のある上限ではない。
- 読み取り専用の故障でDBのコンテナを作り直すときも、同じファイルを置いてから起動する。
- 置いたファイルの出所・置き場所・大きさ・SHA-256を、実行記録に残す。

**2. コンテナに別のホスト名を付ける（`aliases`）。**

- コンテナの名前は、英小文字・数字・ハイフンに限っている。試験用の資源の名前に使うためである。配布物が互いを呼ぶ名前（`db.openelis.org` など）は、別名として書く。
- 外部通信を遮断した試験では、対象の名前を中継が受け持っている。別名も中継が受け持つ。通信の記録は、別名で届いた接続も同じ対象への接続として数える。
- 別名が、ほかのコンテナの名前・別名・中継用の接続先名と重なる指定は拒否する。重なると、どちらに届くかが決まらない。

**3. 終了を待つコンテナ（`ready: "completed"`）。**

- 終了コード0で終わったときに、準備できたとみなす。0以外の終了コードと時間切れは、ログの末尾つきで準備できなかったと記録し、後のコンテナを起動しない。
- 待ち受けを持たないので、ポートを割り当てず、中継を置かず、ホストへも公開しない。`expose` は書かない。データベースの役割、文を記録する中継の対象、ブラウザの操作先には指定できない。
- `start_after` と合わせて、「このコンテナが終わってから起動する」を表せる。

**OpenELISのレシピで確かめたこと。**

- 配布物の `configs/properties/common.properties`、`configs/nginx/nginx.conf`、`configs/certs/ensure-stores.sh` を、書き換えずに置いて通った。コンテナは配布物と同じホスト名で互いを呼ぶ。`certs` は配布物と同じコマンドで動いて終了する。
- レシピに残る配布物との違いは、起動しないサービス（FHIRサーバー、分析装置の中継、自動の再起動）、名前を付けたボリュームに置き換えたホストのディレクトリ、差し込まなかった任意の設定（翻訳、メニュー、検査項目の一覧など）である。

## 2026年11月16日 3件目の実在アプリ（OpenELIS Global 2）を通し、スキーマの指定と起動の順番を足す

OpenELIS Global 2（3.3.0）の患者登録を、`src/` を変えずにレシピだけで通せるか試した。5つのコンテナは起動し、画面の操作は最後まで進んだが、DBの行を読めず、判定は「判定できない」だった。通らなかった箇所は5つあった。このうち2つを基盤で直し、3つはレシピの側の回り道のまま残している。レシピと実行の結果は `examples/openelis-browser/README.md` にある。OpenELISに合わせた処理は足していない。

**1. PostgreSQLで、`public` 以外のスキーマの表を読めなかった。**

- 候補の規則を版3にした。`public` 以外のスキーマの表は、`schema` を付けた読み出しの設定として候補にする。`public` の表の候補は、版2と同じ形である。

**2. コンテナの起動の順番を指定できなかった。**

- 確かめたこと：基盤は、役割の順（DB、その他、アプリ）と一覧の順で、1つずつ起動していた。OpenELISの入口のnginxは、起動するときに転送先の名前を解決する。アプリのコンテナより先に起動すると、`host not found in upstream` で終了する。配布物は、再起動の設定でこれをやり過ごしている。基盤は再起動なしで起動する。
- 入口の役割を「アプリ」、アプリ本体の役割を「その他」と書けば順番は合うが、役割が実態と逆になる。
- コンテナの設定に `start_after` を足した。名前を挙げたコンテナの準備ができた後に起動する。指定のないコンテナの順番は変わらない。存在しない名前、自分自身、重複、互いを待つ指定は、設定の検査で拒否する。

**3. 基盤のHTTPの要求が、要求を転送するnginxで中断とみなされた。**

- 送信側を閉じる処理を外した。要求の終わりは `Content-Length` で分かるので、閉じる必要がない。同じ処理を使うHTTPの操作（`http` の操作と読み出し）も変わる。TLSの要求は別の経路（curl）で、変えていない。

**レシピの側の回り道のまま残したこと。**

- 設定ファイルをコンテナへ渡す手段がない。OpenELISのアプリは、ホストから差し込む `/run/secrets/common.properties` がないと初期化に失敗する。レシピでは、内容を環境変数に入れ、別のコンテナに共有ボリュームへ書かせた。

- 1回動いて終わるコンテナを表せない。配布物の `certs` は証明書を用意して終了する。レシピでは終了しないコマンドに置き換えた。
- この3つを基盤で表せるようにする変更は、入力の形と上限を決める必要があるので、設計の案を先に作る。

**確かめたが、基盤の変更が要らなかったこと。**

- 自己署名の証明書のHTTPSの入口は、既存の `tls` の指定で操作できた。

## 2026年11月12日 2件目の実在アプリ（OpenMRS 3）を通し、起動と後始末の3点を直す

OpenMRS 3.8.0 の患者登録を、`src/` を変えずにレシピだけで通せるか試した。通らなかった箇所は、起動待ちの上限の1点だった。試す途中で、対象によらない不具合を2点見つけた。3点とも、OpenMRSに合わせた処理は足していない。レシピと実行の結果は `examples/openmrs-browser/README.md` にある。

**1. コンテナの準備を待つ上限が5分だった。**

- 確かめたこと：OpenMRSのバックエンドは、初回の起動でDBのスキーマを作る。4コアの作業環境で、準備できるまで781秒と791秒かかった。上限の300秒では、試行は「判定できない」で終わった。期待と異なる、とは判定されなかった。
- `container::MAX_READY_MS` を1800000ミリ秒（30分）にした。上限はコンテナ1つごとの値で、レシピが `ready_timeout_ms` に書いた時間だけ待つ。既存のレシピが待つ時間は変わらない。
- 30分は、実測の約13分に対して2倍強の余裕を持たせた値である。これより遅い対象や環境で足りるかは確かめていない。
- 故障を解除した後の待機上限（`trial.recovery.ready_timeout_ms`）は、同じ定数を使っていた。`trial::MAX_RECOVERY_MS` に分け、300秒のままにした。復旧で待つのは初期化の済んだコンテナで、延ばす根拠を持っていない。
- 準備を待っている間に試行を止める手段は、変更前からない。上限を延ばしたので、準備できない対象を待ち続ける時間は最長で6倍になる。

**2. イメージが宣言したボリュームが、試行の後に残っていた。**

- 確かめたこと：基盤はコンテナを `docker rm -f` で消していた。イメージが `VOLUME` で宣言した場所には、コンテナの作成時に名前を指定していないボリュームができる。このボリュームは `-v` を付けないと消えない。試行のラベルも付かないので、後始末の確認（`eel.trial` のラベルで探す）にも現れなかった。作業環境には、これまでの試験で131個、約5.8GBが残っていた。
- コンテナを消す箇所を `docker rm -f -v` にそろえた。名前を付けて作ったボリュームは `-v` では消えないので、設定に書いたボリュームの扱いは変わらない。
- コンテナを作った直後に、載っているボリュームのうち設定に書いていないものの名前を控える。後始末の後で、控えた名前のボリュームが残っていれば `leftovers` に入れる。名前は実行記録の `containers.image_volumes` に残す。該当するボリュームがない試行では、この項目を保存しない。
- ボリュームの名前を読み出せなかった場合は控えられない。その場合も `-v` で消すが、消えたことは確かめられない。
- `environment run` のコンテナの削除（`src/environment.rs`）にも `-v` を付けた。こちらには、残ったボリュームを確かめる処理を足していない。

**3. 準備できなかったコンテナの記録に、ログの最後の行が残らなかった。**

- 確かめたこと：基盤は、コンテナのログを標準出力と標準エラーに分けて読み、標準出力の全文の後ろに標準エラーの全文をつないでいる。記録に残す抜粋は、つないだ内容の末尾80行だった。標準エラーへ80行以上を書いた対象では、抜粋が標準エラーの行だけになる。OpenMRSのバックエンドは、起動の直後のスタックトレースを標準エラーへ書き、その後の進み具合は標準出力へ書く。時間切れの記録に残ったのは起動の直後の行で、どこまで起動が進んでいたかを読み取れなかった。
- 同じ抜粋は、ログが読み込みの上限（4MiB）を超えた場合にも、対象が最後に書いた行にならない。超えた分は読み捨てるためである。

## 理解とテストの入口の修正

本人の2026-10-07の指定に合わせ、GitHubを読む理解画面とテスト結果を記録する画面を分けた。保存試験の記録画面から始まっていた入口を修正する。

公開APIとraw.githubusercontent.comは利用者のブラウザから読む。GitHubのトークンや取得コードをサーバーへ送らない。コミットを固定して出所の行へ戻る。対象コードをスキャンだけで実行しない。

最初の読解は簡易な宣言・参照の抽出と作者の説明の表示。静的な参照関係を実際の実行経路としない。未知の構文や未読ファイルがあるため完全な理解とは扱わない。コードを条件の出所へ渡しても試験方法は未定義として始める。

以下は今回より前に進めたテスト基盤の選択。

- 共通比較入力からdecisions.basisの自動判定理由・行動提案を除く。元の事例と判断履歴は変えず、人が記入した判断・理由は双方の資料へ同じように渡す。説明を外す表示へ説明が混入する問題を避けるため。

- 空の汎用事例は既存Workspaceを再利用する。条件・質問・回答を自動で作らず、医療特化の要件待ちでも一般の事例を開始できる。アダプター完全分離は次の作業。
- 画面の再描画時は未保存の入力と選択を保持する。未編集の条件文・規則・依存先は最新版へ更新する。ページ終了後の下書きの永続化は含めない。

## 10月13日の固定版の実行・汎用観測

- Gitのコミットから通常ファイルをコピーして、未コミットの作業ファイルを実行しない。origin・コミット・起動ファイル・参照ファイル・行範囲を照合する。symlink・submoduleは扱わない。
- Node.jsとPythonを明示し、依存パッケージは自動で導入しない。JSON入力・引数・観測名・対象を試験設定に保存する。資格情報を含む親の環境変数を引き継がず、試行用の環境変数だけを渡す。Pythonのbytecodeキャッシュが固定版へ作られないようにする。
- 対象コードの観測を共通のJSONLで受ける。識別子・順序・参照先・行を照合し、欠落、別試行、食い違いから成功を補わない。観測の呼び出し元はプロセスの申告で、独立した実行トレースではない。
- 条件ごとの依存先へ試験設定・ランタイム・入力・方式を保存する。違う条件の試験設定を全体の共通値として混ぜない。事例の変更と試行の取り込みは競合を検査し、実行中の変更は上書きしない。
- localは自分で確認したコードの接続用。OSの隔離、子孫プロセス全体の停止、外部状態の復元は保証しない。Linuxのbubblewrapはnamespace・読み取り専用の固定版・試行用workを使い、起動不能時にlocalへ切り替えない。
- 次の確認は明示的な規則で選ぶ。実行・終了失敗は起動設定と標準エラーの確認、固定版の変化や無効な観測は出所の照合、正常終了後の観測欠落は選択した観測名・対象の出力箇所の確認へつなぐ。未回答の利用条件と古い根拠はそれぞれ質問・再試験を優先する。新規性や最適な質問選択を示した意味ではない。

仕様・制限は[pinned-execution.md](pinned-execution.md)。本人の仕様採用、実運用の条件、実参加者の理解、比較での優位性は未確認。

## 画面からの固定版実行（10月13日、#128）

- 起動時に一つのGitリポジトリと方式を指定した場合だけ、画面から固定版を実行する。通常のレビュー画面から任意のファイル・コマンド・取得先を指定する操作は追加しない。
- 一件を別スレッドで実行し、HTTPの閲覧を処理できる状態にする。同じサーバーの二重起動をMutexで拒否する。複数サーバー全体の排他や実行の中断・再開は含まない。
- 受付、起動直前、結果取り込み時に事例の版を照合する。途中の変更では試行を残し、現在の事例を上書きしない。終了・取り込み完了と、業務条件の成功を区別する。
- 完了状態を読んでから事例を読み直す。古い事例の判定を取り込み完了の結果として見せないため。編集中の入力は既存の下書き保持を使う。
- 実行ボタンと設定の保存は同じ入力検査を使う。方式・リポジトリパスは起動時の設定を使い、ブラウザからの上書きを受け付けない。localはOSの隔離ではない。

これは接続操作の試作で、任意アプリの自動計測、医療業務の要件採用、研究の有効性を示すものではない。

## 読み込みの別名と呼び出し元（#129）

- 読み込み宣言のローカル名と参照先の名前を記録し、候補の宣言と対応づける。未読ファイルに仮の関数を作らない。参照先を追加で読むと、同じ固定版の解析を更新する。
- 型や動的な束縛を解決しないため、呼び出し先・元は常に候補として示す。引数や簡単な局所宣言に同名の記述があれば、対応づけを保留する。複雑なスコープの完全な検査ではない。
- 呼び出し元の探索は最大400関数、表示は最大80件にする。未読のコードと上限を表示し、結果がないことを呼び出しがない証明にしない。
- 同じ解析モデルの関数範囲と案内を再利用する。追加読取・版更新でモデルを作り直すため、旧版の対応を新しい版へ流用しない。
- Pythonの拡張子省略を同名のJavaScriptファイルへ解決する反例を修正し、言語ごとの参照先候補を使う。再export・パッケージ内部・動的呼び出しは未対応。

- 画面で既に読んだ事例とサーバーのEvidenceViewを使う。比較のために判定規則をJavaScriptへ複製せず、現在の条件への適用範囲を観測時の判定と分ける。

- 選択を変えたら前の比較を消す。事例の再読込では選択を保持して適用範囲を再計算し、古い表示を現在の適用範囲として残さない。
- 比較資料の保存はJSONのダウンロードに限定する。試行、現在の判定、人の判断、事例版は変えない。結果の変化から改修の因果効果を推定しない。
## 汎用バックエンドv1（#133）

- 医療固有の固定対象の検査と模擬索引の判定を`src/adapters/vitalsensing.rs`へ分離し、既存の保存・固定版実行・医療アダプターの判定を維持する。

- HTTPは最大16件を別スレッドで扱い、途中のリクエストやネットワーク読取でほかの閲覧を止めない。事例への書き込みは従来の排他と版照合を使う。

## 理解と試験の画面（10月14日）

使い方と判定の規則は[understand-and-test.md](understand-and-test.md)、画面の部品は[design-system.md](design-system.md)。次はCodexが試作のために選んだ仕様で、本人が採用した業務の要件ではない。

- 対象の例に [sjl/t](https://github.com/sjl/t) を選んだ。Python標準ライブラリだけで動き、依存関係のインストールが要らない。作業用ディレクトリのファイルへ書き、後から同じコマンドで読み出せるため、「受付」「書き込み」「後から読み出せた」を別々に観測できる。コミット `70817fd` では保存に失敗しても終了コードが0になり、`815ccaf` で1になる。修正前後の比較を、対象の実際の履歴で確かめられる。
- URLを入力したときは、GitHubから一覧と本文を読むだけにする。試験用の取得（`git fetch --depth=1` で固定コミットだけを管理用ディレクトリへ取得）と実行は、利用者がそれぞれのボタンを押したときだけ行う。依存関係のインストールは行わない。
- 読んだ固定コミットのファイルをデータの保存先の `snapshots/` に残す。40文字のコミットを指定して開き直すときは、保存した内容を使い、GitHubへ再度問い合わせない。ブランチ名やタグは指す先が変わるため、毎回問い合わせる。
- GitHubの問い合わせ回数の上限に対応するため、`EEL_GITHUB_TOKEN_FILE` で読み取り用のトークンを指定できる。トークンはサーバーが読み、環境変数を消した読み取り処理（Node.js）へだけ渡す。画面・記録・ログには出さない。GitHubのトークンは長さと形式が変わるため中身を解釈せず、要求ヘッダーを壊す空白・改行・制御文字と、4096文字を超えるものだけを拒否する。
- 実行環境は、PATHで見つかった `node`・`python3` に実体のパスを尋ねて決める。pyenvなどのシェルスクリプトは、環境変数を消した試行で動かないため。見つからない、または起動できない場合は、画面に「利用できない」と理由を表示し、実行ボタンを止める。
- 期待・実装の説明・指摘・質問は、基盤が記入者・事例の版・条件の版を記録する。確認は名前と役割を添えて、記録した人とは別に残す。運用担当と開発者の両方が現在の条件の版で確認したときだけ「両者が確認済み」と表示する。条件を変えると「再確認が必要」に戻る。名前と役割は利用者の自己申告で、本人確認は行っていない。
- 「合意済み」という状態は作らない。判断の記録は、記入した人の判断として表示する。
- 一つの判定の範囲を、別々の方法で観測した結果が食い違う場合は「判定できない」とする。そのため故障の試験案では、終了コード・エラー表示・書き込みを別の範囲に分ける。
- AIの説明は、サーバーで設定（`EEL_AI_BASE_URL`・`EEL_AI_MODEL`・`EEL_AI_API_KEY_FILE`）したときだけ使う。固定コミットの抜粋を渡し、返った説明の引用ファイル・行が実在するかをサーバーで照合する。未設定・失敗のときは、その状態を表示し、固定文で補わない。静的な解析と質問への回答は続けて使える。

確かめていないこと：医療業務での利用条件、実際の運用担当と開発者がこの画面で理解できるか、ほかの言語・依存関係を持つ対象での試験、複数人の同時編集、外部公開時の認証。

## 固定した依存先と複数のプロセス（#137）

#138の一つ目。対象の例に [pynetdicom](https://github.com/pydicom/pynetdicom)（v3.0.4、`2692cb9`）と、依存先の [pydicom](https://github.com/pydicom/pydicom)（v3.0.2、`20aa4b7`）を選んだ。DICOMの送信（storescu）と受信（storescp）が別のプロセスで、受信側が保存できずに失敗の状態（0xA700）を返しても、送信側の終了コードは0になる。終了コードだけでは保存を判断できないことを、医療系の実際のOSSで確かめられる。次はCodexが試作のために選んだ仕様で、本人が採用した業務の要件ではない。

- 依存先は、利用者が指定したリポジトリと40文字のコミットだけにする（最大8件）。基盤が `git fetch --depth=1` で取得し、ファイルを試行ごとに読み取り専用で複製する。`pip install`、ビルド、対象のインストールスクリプトは実行しない。版の範囲の解決や、依存先の依存先を自動で取得することもしない。
- pydicomなどは `importlib.metadata` で自分の版を読むため、インストールしないと起動できない。基盤が、固定コミットの `pyproject.toml` の `[project]` に書かれた名前・版・scriptsだけから、最小の配布情報（`*.dist-info`）を作る。`dynamic` で版や名前を決める対象には作らず、作らなかったことを記録する。作った配布情報は記録に残し、インストールした結果とは扱わない。
- Pythonは `-S -P` で起動し、読み込み先を「対象の読み込み先」「依存先」「生成した配布情報」の順に固定する。利用者の環境のsite-packagesと作業ディレクトリを読み込まないため。`-P` を使えないPython 3.10以前では、依存先を使う試行を受け付けない。
- 起動のしかたは、ファイル・モジュール（`python -m`）・pyprojectのscriptsの3つ。モジュールとscriptsは、固定コミットのファイルに実在するかを試行の前に確かめ、実際に起動したファイルを記録する。
- 受信側のような先に起動して待つプロセスは、試行ごとに基盤が空いているポートを選び、引数の `{{port}}` に入れる。ポートへ接続できたら準備できたとし、待機の上限（最大60秒）までに準備できない、または停止の前に終了した場合は判定できないとする。ポートを選んでから起動するまでに別のプロセスが使う可能性は残る。停止は終了のシグナル（SIGKILL）で行うため、受信側の終了時の処理は観測しない。準備の確認のための接続を、受信側は1回の接続として扱う。
- 待つプロセスの出力は、操作するプロセスの出力とは別の観測の方法（待つプロセスの出力）にする。どちらも対象プログラムの報告で、基盤による保存先の読み出しとは区別する。
- 故障に、保存先のディレクトリを書き込み不可にする、待つプロセスを起動しない、を加えた。前者は書き込めないことを確かめてから起動し、書き込めてしまう環境では故障が効かなかったとする。
- 引数の `{{source}}` は、固定コミットの複製の場所に置き換える。対象のテスト用ファイル（pynetdicomの `CTImageStorage.dcm`）を入力に使うため。
- bubblewrap方式では、プロセスごとに別のネットワークになり、待つプロセスへ接続できない。そのため待つプロセスのある試行は、local方式へ切り替えずにエラーにする。

確かめていないこと：bubblewrap方式での複数プロセスの試行、PythonのC拡張やビルドが必要な依存先、Node.jsの依存先、医療機関の稼働環境でDICOM通信を試す条件（接続先、AEタイトル、保存先の扱い）。

## 試験専用コンテナ（#139）

- Dockerのエンジンに接続できないときは、その理由を返して試行を始めない。localやbubblewrapへは切り替えない。bubblewrap方式とコンテナの組み合わせも受け付けない。
