# 実際のAIエージェントを通した、画面からの一往復（2026年11月6日）

本人の依頼（2026年11月6日）：実際の mugiurushi-ai をローカルで起動し、`gpt-6.1-terra` を設定して、麦漆の画面から「プレビュー → 架空データとして確認 → 案を受け取る → 採用 → 既存の試験を実行 → 結果説明」を1回通し、どこまで通ったかを記録する。OpenEMRの実機は使わず、再現できる架空の readback 事例でよい。

## 実行したもの

| 項目 | 値 |
| --- | --- |
| 麦漆 | `claude/agent-integration`（`bf3061c` に `tools/agent-live.mjs` を加えた作業ツリー） |
| mugiurushi-ai | `5b8db7ad68d1e0b0f391d88f346fd8fd128b2273`（PR #1 の先頭） |
| モデル | `gpt-6.1-terra`（APIが返したモデル名も `gpt-6.1-terra`） |
| 対象 | 公開リポジトリ `sjl/t` の `70817fd5264caa926fd8ee88b52dfc7d25f4240c`（架空のタスクを追加し、一覧で読み直す） |
| 送ったデータ | 架空の確認項目の文と、確かめたい部分の文・状態だけ（下記）。実患者の情報・認証情報・生のログは無い |

再現の手順（`tools/agent-live.mjs`）：

```sh
cargo build --locked
MUGIURUSHI_AI_DIR=<mugiurushi-ai のチェックアウト> MUGIURUSHI_AI_MODEL=gpt-6.1-terra MUGIURUSHI_AI_AUTH=proxy \
  node tools/agent-live.mjs
```

`MUGIURUSHI_AI_AUTH=proxy` は、プロキシが api.openai.com への認証を付ける環境の場合。キーを使う場合は `OPENAI_API_KEY`。スクリプトは mugiurushi-ai を試行ごとの共有トークンで起動し、麦漆の画面版を `EEL_AGENT_URL`・`EEL_AGENT_TOKEN_FILE` つきで起動して、Playwrightで画面を操作する。この開発環境ではGitHub APIで `sjl/t` を読めないため、gitで取得したファイルから読取記録を作って置く。実行の取得は `git fetch` で行う。記録は `test-results/agent-live.json` と画面写真 `test-results/agent-live-*.png`（リポジトリには含めない）。

## 1回目の実行（記録として残す）

1回目も全段階が完了したが、スクリプトが最初の案（「保存先に…書き込まれる」）を機械的に採用し、判定条件 `c3`（後からの読み出し）に対応づけていた。麦漆は人の対応づけのとおり「観測した」と判定する（対応づけの適否は判断しない設計）。AIの説明はこの点について「保存先への書き込みを直接確認した結果は、この詳細には記載されていない」と書いた。2回目から、判定条件に合う観測の種類を挙げた案を選ぶようにスクリプトを直した。対応づけが確認項目に適切かは、人が確かめる。

## 確認できたこと・できていないこと

- 確認できた：実際の mugiurushi-ai と実際のモデルを通して、麦漆の画面からの一往復（送る内容の確認、架空データの確認を経た送信、案の受け取りと表示、人の採用と保存、既存の判定条件での試験、状態を変えない説明）が通ること。
- 確認していない：案と説明の内容の品質（1事例・各1回）。OpenEMRの実機での一往復。ガイドライン照合の画面（未接続）。応答時間の上限に近い場合の画面の挙動。
