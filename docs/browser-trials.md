# ブラウザ操作の試験

`runtime: "browser"` のRecipeで、試験用コンテナの画面をChromiumから操作する。既存のAPI・CLIのRecipe読込を使える。`npm ci --ignore-scripts` と `npx playwright install --with-deps chromium` がサーバー側に必要。Playwrightはpackage-lockで固定し、`browser.expected_version` と実際のブラウザの版が一致しなければ操作を始めない。版は `node_modules/playwright-core/browsers.json` に記載される。

ChromiumはPlaywrightに固定された通常版をheadlessモードで起動し、OSのサンドボックスを有効にする。起動できない環境では試験を未完了として記録し、`--no-sandbox`へ切り替えない。UbuntuでAppArmorがuser namespaceを制限する場合、CIは導入済みChromeのsandbox helperを使うか、固定したChromiumの実行ファイルの正確なパスだけをAppArmorの例外にする。OS全体のuser namespace制限は解除しない。ローカル環境でも[Chromium公式の手順](https://chromium.googlesource.com/chromium/src/+/main/docs/security/apparmor-userns-restrictions.md)に従ってサンドボックスを用意する。Nodeの制御処理自体はホストで動き、ブラウザのサンドボックスとは別の範囲になる。

流れは、コンテナの準備 → `browser.preparation`（ログインなど）→ 故障の注入 → `browser.actions`（保存など）→ DBの直接読取 → コンテナ停止・掃除。各操作はラベル・役割、またはCSSで対象を指定する。iframeは`target.frames`のCSSセレクターで親から順に選ぶ。任意のJavaScriptを設定から実行する機能はない。

```json
{
  "service": "web",
  "tls": false,
  "start_path": "/",
  "expected_version": "151.0.7922.34",
  "preparation": [],
  "actions": [
    {"id": "message", "action": "read_text", "target": {"locator": {"by": "role", "role": "heading", "name": "Welcome to nginx!"}}}
  ],
  "responses": [],
  "database": []
}
```

これはRecipeの`browser`フィールド。完全な例は`tests/containers.rs`の`browser_observes_nginx_and_preserves_screenshots`にある。`fill`の値は`{"source":"literal","value":"{{test_value}}"}`、または`{"source":"secret","key":"password"}`。秘密の値をRecipeに書かず、サーバーの`EEL_BROWSER_SECRETS_FILE`で渡すJSONから読む。例：`{"password":"試験専用の値"}`。ファイルはサーバー管理者だけが読める権限で置く。ページに投入する認証情報は架空の試験用に限る。

| 判定方法 | `target` | 観測の範囲 |
| --- | --- | --- |
| `browser_text` | `read_text`の手順ID | 完了した試験操作で読んだ表示。保存の証明とは別 |
| `browser_response` | `responses`のID | 試験操作中の要求に対するHTTP応答。`status=200`、`body_match=true`または`body_match=false`を照合 |
| `database_rows` | `database`のID | MariaDBから試験値に一致する行を直接読んだ結果 |

`responses`にはID、同じ試験用オリジン内の`path`、`method`、任意の`contains`を指定する。本文は保存せず、指定文字列が含まれるかだけを記録する。Cookieの値とクエリーは記録しない。応答ヘッダーは、下の「画面の構造とHTTPのやり取りの記録」に挙げた7つの名前だけを記録する。準備時の応答は判定に使わない。200件の記録上限に達した場合は、記録できた応答だけで成功としない。同じ観測先で条件を満たす応答と満たさない応答が混じった場合は未観測扱いとする。本文が取れなかったことを「含まれない」の成功にはしない。

`database`にはID、DB役の`service`、`database`、`table`、`match_column`、`columns`を指定する。PostgreSQLで表が`public`以外のスキーマにある場合は、`schema`にスキーマの名前を書く。省略すると、接続する利用者の検索の順（search_path）で表を探す。MariaDBでは`database`がスキーマにあたるので、`schema`の指定は拒否する。識別子は英数字と下線だけで、検索値は基盤が作る試行ごとの架空の値。任意のSQLは受け取らない。正常終了した読取で0行なら、その値に一致する行がないことを記録できる。DB停止・認証失敗・出力超過の場合は不在とは判定しない。MariaDB以外のDB、複数テーブルの結合、実際の業務上の閲覧権限は未対応。

記録は`execution.json`内の`containers.browser`と`containers.database_reads`、画面写真は試行の`browser/`へ置く。途中失敗も完了した手順と停止した手順を残す。認証入力直後の画面写真を省き、その後も入力欄をマスクする。エラーや文字列では秘密の値を伏せる。ただし、対象アプリが別の場所へ秘密を反映する画面まで自動で隠す保証はない。結果画面から開く方法は後述する。

手順が未完了となった場合は、その直後の画面写真を一度だけ、最大1秒で取得する。操作の待機時間を使い切っていても撮影を試みるが、操作の再試行はしない。写真の取得に失敗した場合は理由を手順の記録へ残す。秘密入力の手順では、失敗後も写真を省く。停止後の写真には撮影時点を説明し、写真の有無で操作の完了・保存・条件の判定を変えない。

`read_text`で期待する文字を待ち切れなかった場合、指定した要素が一つだけ表示されていれば、待機終了後の文字を参考記録に残す。取得できない場合は空のままとする。どちらの場合も操作は未完了のままであり、後続の操作は実行せず、この参考記録を成功・失敗の判定には使わない。

ブラウザの通信先は、その試行のコンテナの公開ポートに限定する。Service WorkerとWebSocketは使わない。コンテナ自身の外部通信は、コンテナ設定の`egress`（既定は遮断）で扱う。ページやコンテナは試験用の信頼できる対象に限る。

ブラウザ実行では、Recipeの`source`に指定したファイルだけを固定コミットから複製して、構成を参照した根拠にする。実際に起動するコンテナのコードとそのGitコミットが一致することは、この参照だけでは証明しない。イメージの固定は別のダイジェストとして残す。

#140のうち、操作・三種類の観測・途中失敗の記録を扱う最初の基盤。OpenEMRの患者登録・診療記録、OHIFの一覧・画像表示を実行確認したという意味ではない。

## 画面の構造とHTTPのやり取りの記録

ブラウザ試験は、判定条件とは別に、次の2つを試行の記録に残す。どちらも実行時の観測で、コードの読解による推定とは区別する。観測の種類の一覧では「記録のみ」で、そのままでは判定条件に使えない。

**画面の構造。** 各手順が完了した時点で、試験対象のオリジンのフレームごとに記録する。

- URLのパス、タイトル、見出し
- 入力欄の属性：タグ、種類、`name`、`id`、ラベル、必須、読み取り専用、無効、`autocomplete`、最大長、フォームの送信先のパスとメソッド
- ボタンと、同じオリジンへのリンクのパス
- iframeの入れ子の位置（`name=…`、`id=…`、`src=…`）
- 最上位の文書を最後に読み込んだときの応答の状態、下記の名前のヘッダー、Cookieの名前と属性

**HTTPのやり取り。** 操作の段階で対象のオリジンへ送った要求と応答を、レシピでの宣言の有無によらず記録する。項目は、発生した手順、メソッド、パス、状態、リソースの種類、下記の名前のヘッダー、Cookieの名前と属性である。準備の段階の通信は含めない。

記録しないものは次のとおり。

- 入力欄に入っている値。操作器は `value` を読まない。
- Cookieの値、要求と応答の本文、クエリ文字列。
- 次の7つ以外の応答ヘッダー：`content-security-policy`、`strict-transport-security`、`x-frame-options`、`x-content-type-options`、`referrer-policy`、`cache-control`、`content-type`。

保存と上限。

- 画面の構造は `runs/<試行ID>/browser/screens.json` に保存し、`execution.json` には手順ごとの参照（段階、手順、内容のSHA-256）だけを持つ。SHA-256は基盤が計算する。
- 操作器が書いた記録は、基盤が型と上限を検査してから保存する。検査に落ちた記録は保存せず、理由を残す。試行の判定は変えない。
- 内容が直前と同じ画面は、先行の記録への参照にする。
- 1つのフレームにつき欄300、ボタン200、リンク200、見出し50、1つの画面につきフレーム32、1つの試行につき画面96とやり取り500まで。やり取りは合計512KiBも上限にする。超えた分は捨て、捨てたことを記録に残す。
- 画面の構造を記録していない試行（変更前の記録、準備が完了しなかった試行、検査に落ちた記録）を、画面が空だったとは表示しない。

準備が完了しなかった試行では、画面の構造を保存しない。閉じたShadow DOMの中と、対象のオリジン以外のフレームは記録しない。

## 属性と応答ヘッダーの判定条件

| 観測方法 | 対象 | 期待 | 文 |
| --- | --- | --- | --- |
| `browser_attribute` | `read_attribute`の手順ID | `contains`、`not_contains`、`equal`、`not_equal` | 属性の値 |
| `browser_header` | 応答の観測先のID | `contains`、`not_contains` | `<ヘッダーの名前>: <値の一部>`。値を省くと有無を確かめる |

```json
{"id": "pin-type", "action": "read_attribute", "name": "type",
 "target": {"locator": {"by": "label", "text": "暗証"}}}
```

- 要素はあるが属性がない場合は、観測した結果として扱う。`equal`と`contains`は期待と異なり、`not_equal`と`not_contains`は期待どおりになる。
- 要素が見つからない場合は手順が未完了になり、判定条件は「観測できなかった」になる。属性がないとは扱わない。
- ヘッダーの条件は、上の7つの名前だけを受け付ける。操作の段階の応答を観測していない場合、同じ観測先の応答で結果が分かれる場合、ヘッダーを記録していない変更前の記録の場合は「観測できなかった」になる。
- ヘッダーの値は512文字まで記録する。超えた分を切り捨てたヘッダーは、名前を `headers_truncated` に残す。記録した部分に条件の文字があれば「含む」と判定する。記録した部分にない場合は、切り捨てた部分にあるかもしれないので、`contains` も `not_contains` も「観測できなかった」になる。画面の記録と通信の記録に残すヘッダーには、切り捨ての印を付けていない。この2つは判定に使わない。

## 入力した値の追跡

ブラウザの設定で `track_values` を有効にすると、入力した試験値がどこに現れたかを基盤が記録する。試験値は試行ごとに一意なので、対象のスキーマやURLを指定しなくても探せる。記録は判定に使わない。

```json
"browser": { "track_values": true, "value_per_step": true, "...": "..." }
```

追跡する値は、試験値そのものと、試験値を含む文字を入力した手順ごとの、入力した文字の全体である。秘密値の入力と、試験値を含まない入力は追わない。`value_per_step` を有効にすると、入力の手順ごとに `<試験値>-01`、`<試験値>-02` のように異なる値を入れる。同じ文字を複数の欄に入力するレシピでは、これを使わないと、どの欄の値がどこに現れたかを区別できない。

| 場所 | 調べ方 | 記録 |
| --- | --- | --- |
| DB | 操作の前後に、文字列型の列をすべて調べる。列ごとに、値を含む行の数と、値と等しい行の数を数える | `containers.database_scan_before`、`database_scan` |
| HTTP | 操作の段階の要求（クエリ文字列と本文）と、応答の本文に値が含まれるかを調べる。本文は残さない | やり取りごとの `request_slots`、`response_slots` |
| 画面 | 各手順が完了した時点で、表示されている文字列に値が含まれるかを調べる | 手順ごとの `visible_slots` |
| ログ | コンテナの標準出力と標準エラーに値が含まれるかを調べる | `containers.value_trace` |

値ごとのまとめは `containers.value_trace` に残る。DBは、操作の前後の探索を比べた、操作で増えた出現である。

- 値を含む行の数（`rows`）と、値と等しい行の数（`exact_rows`）を、それぞれ前後の差で数える。操作の前の数は `rows_before`、`exact_rows_before` に残す。
- 操作の前の探索がその表を調べていない場合は、差を計算しない。その出現には `baseline_unknown` を付け、操作の後の数をそのまま残す。操作の前の探索がない場合、実行できなかった場合、途中で止めた範囲、照会に失敗した表が該当する。この出現を、操作で現れたものとして扱わない。
- 件数の差では、同じ場所で行の削除と追加が同数あった場合と、前からある行が書き換えられた場合を見分けられない。行が減った場所があれば、`value_trace.limits` に残す。

DBの探索には、全体で90秒の制限時間がある。列の一覧の取得、各照会、照会を止める操作を合わせた時間である。

- 照会には、残り時間をDBのサーバー側の制限時間として渡す。実行中の文と、表の施錠を待つ時間の両方に効く。
- 基盤は同じ時間だけ結果を待ち、過ぎたら待つのをやめる。待つのをやめた照会は、その接続を番号で指してDBの側で止め、接続が残っていないことを数えて確かめる。結果は `database_scan.cancel` に残す。ホストの側のプロセスを止めるだけでは、コンテナの中のクライアントとDBの中の照会は止まらないためである。
- クライアントの出力は1MiBまでしか読まない。超えた場合は、読むのをやめて同じ手順で止める。
- 途中で止めた探索は、止めた理由を `stopped`（`deadline`、`stop_requested`、`output_limit`、`client_failed`）に、調べていない最初の表を `unexamined_from` に、照会に失敗した表を `unexamined_tables` に残す。`tables_scanned` と `columns_scanned` は調べ終えた数で、一覧にあった数は `tables_listed` と `columns_listed` である。
- 途中まで得た結果は残す。調べていない表を、値がなかった表として扱わない。
- 実行中の試行に利用者が停止を求める経路は、基盤にまだない。探索は停止の合図を受け取れるが（`Session::scan_database_within`）、その合図を出すのは今のところ試験だけである。

見つからなかったことを、値がないことと扱わない。次の場合は見つけられず、該当するものは `value_trace.limits` に残る。

- 暗号化、ハッシュ化、符号化された値。文字列型でない列。
- 識別子に英数字と下線以外を含む表と列。調べなかったことを `skipped` に残す。
- 表2000、列20000の上限を超えた範囲と、90秒の制限時間までに調べ終えなかった範囲。`truncated` と、上に書いた範囲の記録に残す。
- ページが本文を読まなかった応答と、1MiBを超える本文。`response_unread` に残す。
- 入力欄の中の値と、画像の中の文字。
- DBが止まっている試行。探索を実行していないことを `performed: false` で残す。

`value_per_step` を使うと、試験値と等しいことを前提にした手書きの読み出し先と判定条件は一致しなくなる。追跡から作った候補と組み合わせて使う。

### 読み出し先と判定条件の候補

`mugiurushi case draft CASE_DIR --evidence EVIDENCE_ID` は、値を追跡した試行から、読み出し先と判定条件の候補を出す。事例は変更しない。候補は、採用してレシピに書くまで判定に使われない。

規則の版3は次のとおり。どの対象にも同じ規則を適用する。

| 観測 | 候補 |
| --- | --- |
| DBで、値と等しい行が操作で増え、操作の前には等しい行がなかった列 | その列を読む設定と、行に値が含まれるという条件 |
| 値を含む要求に、2xxの応答が返った | その応答の観測先と、状態の条件 |
| コンテナごと | ログに試験値が出ないという条件 |

- 同じ値が複数の表や列に現れた場合は、すべてを候補にする。基盤は1つに絞らない。
- PostgreSQLで`public`以外のスキーマの表に現れた場合は、読み出しの設定に`schema`を付けて候補にする。版2までは、この場合を候補にせず、理由を `skipped` に出していた。
- 値を含むだけで等しい行がない列は、等値で読む既存の設定で表せないので候補にしない。理由を `skipped` に出す。
- 操作の前から値と等しい行があった列は、候補にしない。等値で読む設定は前からある行も読むので、今回の保存を確かめる条件にならないためである。等しい行が増えていても同じである。
- 操作の前の探索が調べていない表での出現（`baseline_unknown`）は、候補にしない。
- 同じ文字を入力した値は区別できないので、最初の1つだけから候補を作る。
- 画面に表示されたことは、読む要素を指定する手順が要るため候補にしない。表示された手順を `skipped` に出す。
- 候補には出所（試行、規則の版、`value_trace`）が付く。採用するときは、出所を `browser.provenance` に書く。出所がレシピにない項目を指す場合、レシピの検査で拒否する。

`node tools/recipe-count.mjs <レシピ>` は、セレクタ、通信のURL、DBの読み出し先、判定条件の数を、出所の記録の有無で分けて数える。数は記述の量を示すだけで、試験の妥当性は示さない。

## 操作の記録

`node tools/browser-recorder.mjs --origin http://127.0.0.1:PORT --out NEW_FILE [--secrets FILE] [--test-value TEXT]` は、画面を表示するブラウザで人が行った操作を、レシピの手順の形で書き出す。対象は、試験環境で起動済みのものを指定する。

- 要素の指定は、ラベル、役割、CSSの順に試し、そのフレームの中で一意になった最初のものを使う。iframeは、親のフレームの中で一意なセレクタで指す。
- 一意かどうかは、要素を押し始めた時点の画面で調べる。クリックで画面が変わる要素（ログインのボタンなど）は、クリックの後では押す前の画面を調べられない。キーボードで押した場合は、クリックの時点で調べる。
- チェックボックスやラジオボタンに結び付いたラベルを押した操作は、ラベルへのクリックとして記録する。ブラウザが続けて欄へ送るクリックは記録しない。見た目を作り込んだ部品は、欄そのものを隠してラベルを押させるので、欄へのクリックは再実行で押せない。ラベルは、結び付いた欄のIDで指す。
- クリックの後に対象が送った書き込みの要求（POST、PUT、PATCH、DELETE）の応答が、次の操作の前に届いた場合は、人がその応答を待ったとみなす。その要求を応答の観測先（`responses`）として書き出し、クリックの手順に `wait_response` を付ける。付けないと、再実行は応答を待たずに次の操作へ進む。
- パスワード欄への入力と、秘密値ファイルにある値と同じ入力は、値を残さず秘密値の参照にする。`--test-value` で指定した文字を含む入力は、その部分を `{{test_value}}` に置き換える。
- 同じ欄への続けての入力は、1つの手順にまとめる。
- 一意に指せなかった操作は手順にせず、`problems` に理由を出す。
- 記録した手順は、既存の検査と実行器でそのまま使う。再実行で通らない手順を、記録の側で書き換えることはしない。
- 画面の表示を読む手順（`read_text`）は作らない。何を確かめるかは、人が書く。
- Enterキーでの送信、ドラッグ、ファイルの選択、URLを直接開く移動は記録しない。GETの要求の応答を待ったことも記録しない。待った応答のパスが実行のたびに変わる場合（IDを含むパスなど）は、再実行で一致しない。コンテナの起動は行わない。

`node tools/recipe-live.mjs <レシピ> <名前> --track-only --adopt` は、入力した値を追跡した試行の候補（DBの読み出し先、応答の観測先、判定条件）をレシピへ取り込み、もう一度実行する。判定条件は、候補が作る種類（DBの行、HTTPの状態、コンテナのログ）を候補に置き換え、ほかの種類（画面の表示、DBの行どうしの対応など）はレシピのものを残す。DBの読み出し先は候補に置き換えるが、残した判定条件が参照する読み出し先は残す。値の割り当て（値の追跡と、手順ごとの値）は、候補のもとになった試行のままにする。取り込みの処理は `tools/recipe-adopt.mjs` にあり、`npm run test:recipe-adopt` で確かめる。

## DBへ送った文の記録と、途中での切断

コンテナの設定で `relay` を指定すると、対象の手前の中継を、DBのプロトコルを解釈する中継に置き換える。対応しているのはMariaDBとMySQLのプロトコルである。

```json
"containers": {
  "services": ["..."],
  "relay": { "service": "mysql", "protocol": "mysql" }
}
```

中継は、基盤の実行ファイル自身を試験用のネットワークの中のコンテナで動かしたものである。対象の起動時の初期化を試験の操作と混ぜないよう、基盤が「準備」「操作」の段階を知らせた後の文だけを数える。

記録するのは、書き込み、トランザクションの操作、追跡する値を含む文である。項目は、接続、通し番号、段階、文の種類、最初の表の名前、リテラルを除いた形のハッシュ、同じ形の文の何回目か、追跡する値の出所、最初の応答、応答の後にトランザクションの中か、書き込みが確定した時点か、である。読み出しなどは、種類ごとの数だけを `statement_totals` に残す。

- SQLの本文と値は記録しない。
- 自動コミットの書き込みは、その応答を確定の時点とする。トランザクションの中の書き込みは、COMMITの応答を確定の時点とする。
- 中継は、接続の開始時に暗号化と圧縮の機能を外して、通信を平文に保つ。対象が暗号化を必須にしている場合は接続が成立しない。暗号化された接続を受けた場合は、解釈をやめてそのまま転送し、読めなかった接続の数を記録に残す。
- 記録は5000件まで。超えた分は捨て、捨てたことを残す。
- 既存の接続の集計（接続元、接続先、件数、バイト数）は、同じ中継の記録から従来どおり作る。

**途中での切断。** 故障に `relay_cut` を選び、`relay.cut` で文と時点を指定する。

```json
"relay": { "service": "mysql", "protocol": "mysql",
           "cut": { "shape": "<文の形のハッシュ>", "occurrence": 1, "phase": "after_forward_before_reply" } }
```

| `phase` | 切る時点 | DB | 対象 |
| --- | --- | --- | --- |
| `before_forward` | 文をDBへ送る前 | 文を受け取らない | 接続の切断を受け取る |
| `after_forward_before_reply` | 文をDBへ送った後、応答を対象へ返す前 | 文を処理している | 結果を知らずに、接続の切断を受け取る |
| `after_reply` | 応答を対象へ返した直後 | 文を処理している | 成功の応答を受け取った後、接続が切れる |

- 文は、形のハッシュと、段階を知らせた後から数えた回数で指定する。通常時の試行の記録から選ぶ。
- 中継が指定した文に到達しなかった試行は、故障を適用できなかった試行として判定不能になる。食い違いなしとは扱わない。
- `relay_cut` の故障と `relay.cut` の指定は、必ず組で指定する。片方だけの設定は拒否する。

制約は次のとおり。

- 中継を置けるのは、外部通信を遮断した試験だけである。
- 中継のコンテナの土台は、ダイジェストで固定したUbuntu 24.04のイメージである。基盤の実行ファイルがその中で動かない場合（Linux以外のホスト、glibcの世代の違い）は、中継を起動できず、試行は始まらない。`EEL_RELAY_BINARY` で、中継として動かすLinux向けの実行ファイルを指定できる。
- PostgreSQLのプロトコルには対応していない。
- 16MiBを超えて分割されたパケットの2つ目以降は、文として解釈しない。

## 画面から選ぶ試験の一覧

画面で選べる試験は、運営者が`EEL_RECIPE_DIR`で指定したディレクトリの`*.catalog.json`から作る。ディレクトリの直下と1段下を名前順に読み、シンボリックリンクは読まない。基盤のバイナリは対象の試験を含まない。

```json
{
  "schema_version": 1,
  "base": "soap-recipe.json",
  "note": "架空の患者と診療記録で試します。",
  "entries": [
    { "id": "openemr-soap", "title": "SOAPの保存と再表示" },
    { "id": "openemr-soap-db-stopped", "title": "SOAPの保存直前にDBを停止",
      "fault": "database_stopped", "fault_before_step": "save-soap",
      "keep_checks": { "id_prefix": "soap-" } }
  ]
}
```

- `base`は、一覧のファイルと同じディレクトリから見たレシピの相対パス。`..`や絶対パス、リンクは拒否する。
- `fault`は、もとのレシピの故障を置き換える。
- `fault_before_step`は、その手順より前の操作を準備へ移す。故障は準備の後に入るので、その手順の直前に故障が入る。
- `keep_checks`は、残す判定条件を`ids`か`id_prefix`で指定する。`add_checks`は判定条件を足す。
- 指定した手順や判定条件がレシピにない場合、足す条件のIDが重複する場合、派生したレシピが検査に通らない場合は、一覧の読み込み全体が失敗する。一部だけを黙って省かない。

OpenEMRの3件は`examples/openemr-browser/soap.catalog.json`にある。`EEL_RECIPE_DIR=examples`で起動すると、変更前にバイナリへ含めていた一覧と同じJSONを返す。同じであることは`src/browser_recipes.rs`のテストで確かめる。

## DBの種類

基盤がDBを直接読むときのクライアントとSQLの書き方は、DBの役割のコンテナの`engine`で決める。イメージの名前からは推定しない。

| `engine` | 読み出し | 認証情報 |
| --- | --- | --- |
| 省略、`mariadb` | コンテナの中の`mariadb`クライアント | `MYSQL_ROOT_PASSWORD`か`MARIADB_ROOT_PASSWORD` |
| `postgres` | コンテナの中の`psql` | `POSTGRES_USER`（省略時は`postgres`）と`POSTGRES_PASSWORD` |
| `other` | 行わない | なし |

- 省略した設定はMariaDBとして読み、保存するときも項目を出さない。既存のレシピの内容と、判定条件の指紋は変わらない。
- `other`では基盤が照会を行わず、DBの行を使う判定条件は「観測できなかった」になる。行がなかったとは扱わない。
- PostgreSQLでは識別子を二重引用符で囲むため、表と列の名前は大文字と小文字を区別する。照合する列は文字列へ変換して比べる。
- DBの停止、切断、ボリュームの読み取り専用化は、種類によらず同じ操作で行う。
- 対応している種類は、この表の2つだけである。種類ごとの差は`src/database.rs`にまとめている。

## 結果画面で観測と画面写真を開く

事例の「ブラウザの観測と画面写真」を開くと、準備・試験操作の完了状況、表示の文字列、HTTP応答、DBの直接読取を別の欄で確認できる。各手順の「画面写真を開く」で、撮影時の写真をダイアログに表示する。写真がなくても、元の判定と観測記録を書き換えない。

写真の読取には`GET /api/v1/browser-screenshot/{evidence_id}/{step_id}`と`X-Review-Token`が必要。基盤は事例に登録した試行と手順からファイルを決め、任意のパスは受け付けない。事例内の`runs/{run_id}/browser/`にある宣言済みのPNGだけを読み、symlink・PNGヘッダーがないファイル・4MiB超の画像を拒否する。

現在のバックアップは観測記録のJSONを保存し、`runs/`を含めない。事例の外から取り込んだ試行やJSONだけを復元した事例では、画面写真の元ファイルを本APIでは開けない。その場合は画面に不足を表示する。写真を含めた持ち出し形式は別の実装範囲。
