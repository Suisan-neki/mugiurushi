## 失敗した回（記録として残す）

同じ日に、この成功の前に画面から2回送った回は、いずれも mugiurushi-ai が `HTTP 502`（モデルの呼び出しで `InternalServerError`）を返し、画面に「AIエージェントが処理できませんでした（HTTP 502）」と表示して止まった（候補は表示していない）。その間に同じ内容をスクリプトから直接 mugiurushi-ai の照合に渡した1回は30秒で応答した。失敗はOpenAI APIの一時的な応答と見ているが、原因は確かめていない。さらに前の1回は、画面の待ち時間の上限（300秒）に達して止まった。この回の後に、失敗したときの画面の警告と応答を記録するようスクリプトを直した。

成功した回の前（`7a6adb5` の前）にも1回通しており、候補12件・同じ3件の出典を使った。

## 確認できたこと・できていないこと

- 確認できた：実際の mugiurushi-ai と実際のモデルを通して、麦漆の画面から照合が一往復通ること（送る内容の表示、架空データの確認を経た送信、候補・出典・出典ごとの状態の表示、事例の記録が変わらないこと）。モデルの呼び出しが失敗したとき、画面が候補を出さずに失敗を示すこと。
- 確認していない：候補の中身が適切か（1つの説明で、成功は2回）。たとえば「二要素認証を実装する」の確かめ方に `browser_response` が挙がっているが、その要求が試験で確かめられるかは人が判断する。麦漆が示すのは観測の種類として判定条件にできるかだけ。
- 照合の範囲の限界：モデルに渡す断片は上位12件で、今回は医療情報システムの安全管理ガイドラインや個人情報の文書の断片が選ばれなかった。これらに該当する要求が無いことは意味しない。断片の選び方（文字の2文字の組の重なり）の改善は mugiurushi-ai 側の課題として残る。
- 候補から確認項目を作る操作はまだない（人が自分で書く）。

## 追記：出典ごとに断片を渡すようにした後の実行（同じ日）

上の「照合の範囲の限界」と、候補から確認項目を作れない点を受けて、次を直した。

- mugiurushi-ai `7e3ebd8`：説明と語が重なる断片のある出典ごとに最上位の1件を先に選び、残りを全体の順位で埋める（既定20件）。モデルの応答をストリーミングで受け取る。一括で応答を待つ要求は、この開発環境のプロキシ経由で応答が30秒を超えると HTTP 502 になった（同じ要求をストリーミングにすると32秒で受け取れた）。上の「失敗した回」の502も、この打ち切りによるものとみられる。
- 麦漆 `claude/scan-to-check`：候補に「この候補をもとに確認項目を書く」を加えた。判定条件にできる観測の種類の表示を「この観測の種類は判定条件にできる。ただし、この要求をこの観測で確かめられるかは確かめていない」に改めた。

同じ説明で画面から実行した結果（`resp_028b9a6e3d6c7d0e016aed42194bd887d292a833e0b3cdfe2a`、入力9653・出力2929トークン、送ってから表示まで34秒）：

| 項目 | 結果 |
| --- | --- |
| 出典ごとの状態 | 取り込み済みの11の出典すべてが「断片をモデルに渡した」。提供事業者向けガイドラインは「取り込まれていない」 |
| 照合の候補 | 15件（判定条件にできる観測の種類の候補は9件） |
| 候補から確認項目 | 1件目の候補を入力欄に写し、文を「架空の職員がタスク一覧を開いたとき、…」に直して保存した。出所に照合の候補・出典（OWASP Top 10:2025 A01、SHA-256 `35bcd6cf…`）・モデル・応答IDが残り、観測の種類と確かめる部分は未設定のまま |

この前に、同じ選び方でスクリプトから mugiurushi-ai を直接呼んだ回（`resp_01dfbde6…`）では、候補13件の出典に、医療・介護ガイダンス、個人情報保護法ガイドライン（通則編）、医療機器該当性のガイドラインが入った。医療情報システムの安全管理ガイドラインの断片も渡したが、渡った断片（情報の持ち出し）は候補の出典には使われなかった。出典の中でどの断片を選ぶかは、まだ文字の重なりだけで決めている。英語の文書（ASVS・NIST）は日本語の説明との重なりが「ID」などに限られ、関係の薄い断片が渡ることがある。候補の中身の良し悪しは、引き続き確かめていない。
