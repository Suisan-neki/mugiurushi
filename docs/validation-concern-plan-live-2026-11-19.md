# 実際のモデルで、コードから出た懸念から試験の案を作った結果（2026年11月19日）

照合の作り直し（[#230](https://github.com/Suisan-neki/mugiurushi/issues/230)）で、コードをたどって出た懸念を試験の案の候補にする流れ（#241、#242）を、実際のモデルで試した記録である。偽のAIでしか試していなかった、「懸念が起きていないことを確かめる試験」を実際のモデルが書けるかを見た。

## 対象と方法

| 項目 | 値 |
| --- | --- |
| 懸念 | [前回の試行](validation-investigation-live-2026-11-17.md)のうち、往復の単位でキャッシュを効かせた版の結果（OpenELIS Global 2 の 3.3.0、患者の新規登録、12往復、懸念7件）。往復の調べはたどり直していない |
| 候補 | 7件すべて（確かめ方がすべて「麦漆で動かす」だった）。要求の文は「次のことが起きていないこと：懸念」、出どころは `concern` |
| 添えたコード | 照合をしていないので、読んだファイルはない。懸念の根拠の行の前後10行を行番号つきで23か所（同じ範囲は一度だけ） |
| モデル | `gpt-6.1-terra`（APIが返したモデル名も同じ）。標準の処理 |
| 麦漆 | `claude/concern-plan-live`（`main` の `002f164` に、試行のスクリプトを足したもの） |
| mugiurushi-ai | `claude/evidence-commit`（`main` の `a1ba9be` に、`@コミット` の参照の説明を足したもの） |

再現の手順：

```sh
cargo build --locked
EEL_SOURCE_GIT=<対象のコミットを含むgitのリポジトリ> MUGIURUSHI_AI_DIR=<mugiurushi-ai のチェックアウト> \
  MUGIURUSHI_AI_MODEL=gpt-6.1-terra MUGIURUSHI_AI_AUTH=proxy \
  node tools/concern-plan-live.mjs test-results/investigate-live-<番号>.json
```

スクリプトは、懸念の根拠のファイルだけで麦漆の読取記録を作り、画面と同じ組み立て（`ui/flow-record.js` の `concernPlanCandidate` と `planEvidence`）で試験の案のAPIを呼ぶ。1回目は送る内容の要約とSHA-256を示すだけで、何も送らずに終わる。人が内容（`test-results/concern-plan-live-preview.json`）を確かめて、そのSHA-256を `EEL_APPROVED_PLAN` に入れて実行し直したときだけ送る。

今回送ったのは55,376バイト（SHA-256 `97d9ab41…`）で、公開リポジトリのコードの抜粋と懸念だけである。抜粋に認証情報らしい行がないかを語で探し、見つかったのはパスワードを取り出すコードの行と設定の置き換えの記号（`${datasource.password}`）だけで、値は含まれていないことを確かめた。

## 量と費用

| 入力 | うちキャッシュから読んだ分 | うちキャッシュに書いた分 | 出力 | 費用（標準の単価） |
| --- | --- | --- | --- | --- |
| 14,580 | 0 | 14,577 | 2,435 | 約0.03ドル |

キャッシュの区切りを指定していない呼び出しでも、入力のほぼ全体がキャッシュに書き込まれ、入力の1.25倍の単価がかかった。区切りを指定しないとき（暗黙のモード）は、最後のメッセージの終わりで書き込むためである。1回きりの呼び出しでは、キャッシュに書き込まないほうが安い。

## 結果

7件の候補すべてから、試験の案が1件ずつ作られた。試験にしなかった候補も、未分類の候補もなかった。

| 懸念 | 試験の名前 | 種類 | 観測 | 合格の条件（要約） |
| --- | --- | --- | --- | --- |
| c-1 年齢だけの入力が、推定の生年月日として実測と区別できないまま保存される | 年齢から算出された生年月日と消去時の扱い | ブラウザ | プログラムの観測 | 推定値と実測値を区別できる。月末・閏日の値が期待値に一致する。年齢欄を消すと意図しない日付が保存されない |
| c-2 国民識別番号が、重複確認の要求のURLを通じてアクセスログに残る | 国民識別番号の重複確認とアクセスログ | ブラウザ | 保存先 | 重複確認の要求が出たことを確かめたうえで、アクセスログと転送先に番号が平文で含まれない |
| c-3 TRACEが有効な環境で、患者の識別情報がFHIRのログに残る | FHIRトランザクションのログへの患者情報出力 | ブラウザ | コンテナのログ | 両方のログの設定で、ログに識別情報が含まれない |
| c-4 FHIRへの反映の失敗が、画面の保存結果に出ない | FHIRストア・レジストリ障害時の保存結果と整合性 | ブラウザ | プログラムの観測 | 反映の失敗が利用者に分かる。復旧後に一致するか、未反映であることが明示される |
| c-5 同じ番号の同時登録で、重複した患者ができる | 国民識別番号の並行登録と一意制約 | HTTP | DBの行 | 同じ番号の患者の行は多くとも1件 |
| c-6 重複の拒否の文に、既存の患者の氏名と生年月日が入る | 重複番号の拒否応答とログの情報露出 | HTTP | サーバーの応答 | 拒否の応答とログに、既存の患者の氏名や生年月日が含まれない |
| c-7 緊急連絡先を空欄にしても、空の連絡先の行ができる | 緊急連絡先空欄での患者登録 | ブラウザ | DBの関係 | 空の緊急連絡先の行と、対応する空のpersonの行が作られない |

### よかった点

- 7件とも、懸念が起きていないことを合格の条件にしていた。懸念が起きていることを合格とする向きの取り違えはなかった。
- 手順は、要求のパス（`/rest/PatientManagement`、`/rest/subjectNumberValidationProvider`）、設定名（`ALLOW_DUPLICATE_NATIONAL_IDS`）、表の名前（`clinlims.patient`）まで、根拠の行から拾えていた。
- 分からないところは推測で書かず「（要確認）」とした。画面のURLはすべて要確認だった。照合をしておらず、画面の経路のコードを添えていないためである。

### 弱い点

- 合格の条件の一部は、観測から決められない。c-4の「利用者に分かる」は判断を要する。c-2の2つ目の条件（「ログが存在しない場合は、記録が無効であることを設定から確認できる」）は、1つ目の条件と同時に満たすのか、どちらかでよいのかが分からない。c-5の2つ目の条件は、競合の時機を計測できることを前提にしている。
- 7件のうち4件は、環境の準備が重い。FHIRの送信先を止める（c-4）、TRACEのログを有効にする（c-3）、重複を禁止する設定を変える（c-5、c-6）、同時に登録する（c-5）。設定の方法はどれも要確認だった。
- 同じ登録の操作で確かめられる懸念（c-2、c-6、c-7）も、まとめずに1件ずつの試験になった。指示文は「同じ操作で確かめられる候補は一つの試験にまとめる」としているが、懸念ごとに準備や観測が違うためか、まとめなかった。

## 確認できたこと・できていないこと

- 確認できた：実際のモデルで、懸念の候補から、懸念が起きていないことを確かめる試験の案を作れること。根拠の行の抜粋だけ（読んだファイルなし）でも、要求のパスや設定名まで拾えること。費用は1回で約0.03ドルだった。
- 確認していない：
  - どの試験も動かしていない。合格の条件が実際の観測で決められるかは分からない。コードを読む限り、c-6は懸念が起きる作りなので、試験は不足を確認する見込みである（[前回の記録](validation-investigation-live-2026-11-17.md)で根拠の行を確かめた）。
  - 1回だけの試行で、同じ候補から同じ案が出るかは分からない。
  - 引き継いだ懸念（`@コミット` の付いた根拠）から作る案は試していない。

## 次に試すことの示唆

- すぐ動かせるのは、c-2（マウスが欄から出たときの要求とアクセスログ）、c-6（重複の拒否の応答）、c-7（緊急連絡先を空欄で登録）である。どれも登録の操作だけで、環境の設定を変えずに観測できる。
- 画面のURLを要確認にしないためには、照合で画面の経路のコードを読むか、懸念の根拠に画面の経路の行を含める必要がある。
- 1回きりの呼び出しは、キャッシュに書き込まないようにすると費用が下がる。

## 追記（2026年11月19日）：c-2、c-6、c-7を動かした結果

c-2、c-6、c-7をOpenELISで動かした（[記録](validation-concern-tests-openelis-2026-11-19.md)）。3件とも懸念は実際に起きた。c-6とc-2は麦漆のレシピで「満たしていない」と判定できた。c-7は、麦漆のDBの読み出しで患者の行から連絡先の行をたどれず、レシピで書けなかった。

上の「すぐ動かせる」は誤りだった。c-6は環境の設定を変える必要があった。配布物の初期データが国民識別番号の重複を許しているためで、案の最初の手順（設定を変える）は必要だった。
