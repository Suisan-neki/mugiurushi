# 対話の追加読取とブラウザ試験

## 質問に応じたコードの読取

構成図の対話を送ると、既存の質問用読取を実行する。質問に含まれる名前と一致するパスを優先し、固定コミットから最大8ファイルを補う。PHP、Twig、SQLは本文を読めるが、既存のRust・Python・JavaScript用の構文解析へ対応したとは扱わない。

以前に保存した読取記録でも、ファイル一覧から追加候補を選べる。`SOAP`を含む質問では、`interface/forms/soap/`の保存・表示・テンプレートなどが候補になる。名前を含まない曖昧な質問で、必ず目的の処理へたどれる保証はない。

質問の根拠を構成図の根拠より先に、合計48KiBまで行番号付きでAIへ渡す。本文を読んだことと、その全行をAIへ渡したことは別である。AIの主張は今回渡した行と照合し、範囲外の参照を含む返答は保存しない。参照行の存在は説明の正しさや実行時の挙動の証明ではない。

対話の各往復に、追加で読んだファイル、取得に失敗したファイル、未読候補、文脈の指紋を保存する。画面でも追加読取と取得失敗を表示する。既存の会話形式は引き続き読める。

Difyが以前の`system_context`を使い続けないよう、渡す図とコードが変わった場合はリモートの会話を新しくする。ローカルの対話ID、直近6往復、前の整理案、同じ対話に属する検証結果は引き継ぐ。図とコードが同じ場合は同じリモート会話を使う。

## 画面から選ぶSOAP試験

`/workbench`でOpenEMRの確認項目を選ぶと、同梱のブラウザ試験を選べる。`GET /api/v1/browser-recipes`は既存と同じ操作トークンの検査を使い、選択候補を返す。取得・実行はしない。

- 通常時のSOAP保存・再表示・DB照合。
- SOAP入力後、保存直前にDBを停止してから保存を試す条件。

どちらも`examples/openemr-browser/soap-recipe.json`から作る。DB停止では入力までを準備へ移し、保存操作は試験中に残す。先に保存した患者・受診理由の条件は外し、DB停止後のSOAPの条件を観測する。

確認項目とレシピのコミットが異なる場合は両方を表示し、人が「レシピの版に切り替えて設定する」を押して参照先を更新する。元の相談の出所と過去の根拠は残る。レシピと異なる版で、そのレシピを流用して実行しない。

起動・入力、試す状況、判定条件、実行前の確認を順に表示する。確認画面まで進んでも実行しない。

## 確認項目のどの部分を試験が確かめるか

試験案の判定条件がすべて通ることと、相談された確認項目に答えたことは別に扱う。確認画面で、人が「確かめたい部分」ごとに観測の種類（`GET /api/v1/observation-kinds`）と、この試験のどの判定条件が答えるかを選び、`set_aspects`で登録する。対話から引き継いだ場合はAIの検証案が下書きとして入るが、観測の種類と判定条件は人が選ぶまで未定で、試験が通っても観測済みにならない。相談文と試験の文章が似ているかは自動で判断しない。

対応づけは判定条件の識別子だけでなく、判定条件の内容とその試験設定（操作・引数・観測先など。固定版は除く）の指紋で照合する。手動設定の識別子は並び順の`c1`、`c2`なので、同じ識別子・同じ文面でも範囲・期待・対象や操作対象が変わった試験には適用せず、「対応づけた後に判定条件の内容が変わった」として人が確認し直す。対応づけるとき、麦漆は指紋に加えて、その時点の判定条件と試験設定（コンテナの環境変数の値は伏せる）を確認項目に記録する。画面は`POST /api/v1/link-changes`で保存済みの対応づけと現在の設定を比べ、変わった対応づけについて、何が変わったか（区分・場所・対応づけた時点の値・現在の値）を「現在の内容で対応づけ直す」の前に示す。結果画面も、試行の設定と対応づけた時点の違いを示す。記録のない旧形式の対応づけは、同じ指紋で実行した試行の記録から時点の設定を示し、それもなければ比較できないと示す。別の部分を直して保存しても、変わった対応づけは人が「現在の内容で対応づけ直す」を押すまで以前の指紋を保つ。画面で変えた対応づけは保存するまで判定に使われず、未保存の変更があるうちは「試験を始める」を受け付けない。期待する動作が同じ再検証でも、続けた対話で増えた未確認事項と検証案は確認項目へ引き継ぐ。

結果画面は試験の判定と、部分ごとの状態（観測した、期待と異なる、観測できていない、最新の試行に判定条件がない、観測方法が合わない、判定条件の内容が変わった、未対応づけ、未定、基盤が観測できない、記録や推定だけ、適用できる試行がない）を分けて表示する。登録した部分をすべて観測した確認項目だけが通過になり、「採用する」の判断はそれまで記録できない。外部への送信の有無、通信の中身、分散トレース、本番環境は基盤が観測できない種類として一覧にあり、選ぶと未確認のまま残る。「試験を始める」で既存の準備・実行APIを呼び、確認項目のIDと観測条件を対応づける。準備・操作・HTTP応答・DBの観測先・入力・判定条件のIDを保持し、過去の結果から戻る場合もブラウザ設定を復元する。

## 実行環境と確認範囲

Docker、固定版のPlaywrightとChromium、サーバーの`EEL_BROWSER_SECRETS_FILE`で指定する試験専用の認証情報が必要。認証値は[既存のOpenEMR試験手順](../examples/openemr-browser/README.md)と同じ。画面に実アカウントの入力欄は追加しない。

```sh
npm run test:browser-handoff
npm run test:browser-handoff -- --live
EEL_DIALOGUE_API_ONLY=1 npm run test:dialogue
EEL_DIALOGUE_API_ONLY=1 EEL_DIALOGUE_NATIVE=1 npm run test:dialogue
```

通常の画面試験は合成の読取記録を使い、実行要求を送る直前で止める。`--live`は固定コミットのComposeを読み、画面から実OpenEMRを起動してSOAPの保存・再表示・DB照合を行う。どちらも確認項目は`add_check`で直接登録した固定の文で、AIとの対話は含まない。参照したGitコミットと実行イメージのコードが同一であること、実利用者の理解・改善効果は、この接続確認では証明しない。

読む順番は`src/reader/inquiry.rs`、`src/system_diagram/dialogue.rs`、`src/browser_recipes.rs`、`ui/workbench.js`、`tools/browser-handoff-smoke.mjs`。
