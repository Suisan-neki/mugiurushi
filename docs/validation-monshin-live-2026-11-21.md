# 実際のモデルで、架空の問診アプリの流れを画面から通した結果（2026年11月21日）

照合の流れ（`/flow`）を1画面1操作にし、了承した試験を自動で実行する変更（#251、Suisan-neki/mugiurushi-ai#26）は、偽のAIでしか通していなかった。架空の問診アプリ（`examples/monshin`）で、実際の mugiurushi-ai と実際のモデルを使い、リポジトリの登録から再試験までを画面から通した記録である。応答は毎回変わるので、ここに書くのは今回の実行で観測したことに限る。

## 対象と方法

| 項目 | 値 |
| --- | --- |
| 対象 | 架空のリポジトリ `example/monshin`（`tools/monshin-demo.mjs` が手元に作る）。`main` は受付の職員も回答を読める版、`fix/answer-access` は医師だけが読める版 |
| 送ったもの | `monshin.py`（`README.md` は外した）と、架空の説明、ヒアリングの回答。実在の患者・職員の情報はない |
| モデル | `gpt-6.1-terra`（APIが返したモデル名も同じ）。認証はプロキシ（`MUGIURUSHI_AI_AUTH=proxy`） |
| 文書 | mugiurushi-ai の `ingest --all` で取り込んだもの。提供事業者向けガイドライン（経済産業省のPDF）は、この環境からHTTP 403で取り込めていない |
| 実行の方式 | local方式（OSによる隔離なし） |
| 麦漆 | 1〜2回目は `main` の `314a67d` と途中の変更、3回目以降はこのPRの変更 |
| mugiurushi-ai | 1回目は `main` の `6640250`、2回目以降は指示を補った版（Suisan-neki/mugiurushi-ai の同日のPR） |

```sh
cargo build --locked
MUGIURUSHI_AI_DIR=<mugiurushi-ai のチェックアウト> MUGIURUSHI_AI_MODEL=gpt-6.1-terra MUGIURUSHI_AI_AUTH=proxy \
  node tools/monshin-live.mjs
```

スクリプトは画面を操作し、AIの応答・試験の設定・結果・比較を `test-results/monshin-live.json` に、画面の写真を `test-results/monshin-live-*.png` に残す。応答の中身は検査しない。ヒアリングは、決めた語（既定は「有無のみ」「医師だけ」「医師のみ」）を含む選択肢を選び、合うものがなければ「未定」を選ぶ。

## 結果

| 回 | 説明とヒアリング | `main` の閲覧の試験 | 再試験 |
| --- | --- | --- | --- |
| 1 | 説明は「患者がコマンドで答え、医師が読む」。ヒアリングはスクリプトが最初の選択肢（受付も内容を読める）を選んだ | 試験の設定なし（AIの理由：複数の利用者による読み出しが必要で、単一の読み出しの設定にできない）。未実行 | 満たさない項目がなく、行っていない |
| 2 | 説明に「受付の職員は、回答があるかどうかだけを確かめる」を足した。ヒアリングは「未定」 | 試験の設定あり。満たさない | 照合からやり直した。修正版は満たす。比較は「解消」にならなかった |
| 3〜6 | 2回目と同じ | 4回とも試験の設定あり、満たさない | 了承した試験を引き継いで実行し直した。4回とも「解消」。再試験中のAIへの送信は0回 |

読み込みでは、6回とも「試験環境で動かして確かめます（起動の候補：monshin.py）」になった。照合は20〜27秒、試験の案は17〜33秒、試験の実行は1件で約2秒だった。

AIが作った引数は、2回目以降すべて `monshin.py` の使い方と合っていた（操作は `--dir <.か data> --user P001 answer P001 {{test_value}}`、読み出しは `--dir <同じ> --user reception_b show P001`）。判定条件は「読み出しの出力に `{{test_value}}` を含まない」と、「回答あり」を含む、の組み合わせだった。

### 分かった問題と対処

1. **試験の設定が付かない（1回目）。** AIは、医師・受付・ほかの患者の3人で読み出す試験を考え、1回の読み出しの設定にできないとして設定を作らなかった。指示に、麦漆が1つの試験で動かすのは操作1回と読み出し1回だけであること、要求に反する動きを最も直接に観測できる組み合わせを1つ選び、選ばなかった範囲を注記に書くことを足した（mugiurushi-ai）。注記は試験の案の画面に「この試験では確かめない範囲（AIの注記）」として示す。
2. **要求と関係の薄い判定条件だけが対応づけられ、「満たす」になった（1回目）。** パスの検証の候補の試験で、判定条件は3つ（保存先に試験の値がある、読み出しが0以外で終わる、読み出しの出力に試験の値を含まない）あったが、候補に対応づけられたのは1つ目だけだった。この試験の読み出し（`show ../answers/P001`）は回答を表示するので、3つ目の条件は満たさないはずだが、合否に使われず「満たす」と表示された。指示に、対応づけるのは要求が守られているかで結果が変わる条件であること、観測の方法をそろえること、終了コードの条件は対応づけられないことを足した。画面では、候補ごとにどの判定条件で合否が決まるかと、合否に使わない条件を、了承の前に示すようにした。2回目以降、この形の対応づけは出ていない（5回の実行で観測した範囲）。
3. **ヒアリングの回答が試験の期待に反映される。** 1回目は「受付も内容を読める」と答えたので、受付に表示されることを合格とする案になった。回答は人が選ぶものなので、実装は変えていない。指示には、期待する動作はヒアリングの回答に従うことを明記した。
4. **照合からやり直す再試験では「解消」にならない（2回目）。** 比較は項目を要求の文で対応づけるが、再試験で照合をやり直すと、AIが要求の文を作り直す。`main` は「情報の区分と利用者の職種・担当業務に応じて、利用権限を規定する。」、修正版は「情報の種別・重要性・利用形態に応じて区分し、情報区分ごと、利用者または利用者グループごとの利用権限を規定する。」で、別の項目として並んだ。試験の中身も作り直されるので、同じ試験の実行し直しにもならない。懸念の引き継ぎと同じ考え方で、前のコミットで了承した試験の案を引き継いで実行し直す操作を足した（3回目以降）。

### 前もって進めた記録から続ける流れ

`MONSHIN_DEMO_DIR` を指定して `main` の試験の案の画面まで進めて止め（`MONSHIN_STOP_AT=plan`）、同じ指定で起動し直して続きを実行した。`main` を読み込むと試験の案の画面から始まり、了承・実行（満たさない）・修正用のプロンプト・修正版での実行し直し（解消）まで、AIへの送信0回で進んだ。起動し直すときに、AIへの通信に使うプロキシの指定を届かない宛先に変えた場合も、同じ結果だった。

## 確認していないこと

- 利用者の手元の環境（macOS）での実行。この記録はクラウドの開発環境（Linux、rootで実行）でのもの。
- ネットワークのない端末での起動。プロキシの宛先を変えて通信を遮った状態は試したが、ネットワークのない端末で `uv run` と麦漆が起動するかは試していない。
- ほかのモデル、ほかの説明文、ほかのヒアリングの回答での結果。説明文に受付の職員の扱いを書かない場合に、閲覧の試験がどうなるかは、1回目の1回しか見ていない。
- パスの検証の候補は、2回目以降すべて試験の設定が付かず（試験の前に保存先の外へファイルを置く手段がないため）、未実行のまま。1回目の案の読み出し（`show ../answers/P001`）が実際に回答を表示するかは、コードから読んだだけで、麦漆の試験では確かめていない。
- 指示を足したことで、ほかの対象の試験の案がどう変わるか。
