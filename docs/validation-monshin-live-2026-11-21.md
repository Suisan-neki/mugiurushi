# 実際のモデルで、架空の問診アプリの流れを画面から通した結果（2026年11月21日）

照合の流れ（`/flow`）を1画面1操作にし、了承した試験を自動で実行する変更（#251、Suisan-neki/mugiurushi-ai#26）は、偽のAIでしか通していなかった。架空の問診アプリ（`examples/monshin`）で、実際の mugiurushi-ai と実際のモデルを使い、リポジトリの登録から再試験までを画面から通した記録である。応答は毎回変わるので、ここに書くのは今回の実行で観測したことに限る。

## 対象と方法

| 項目 | 値 |
| --- | --- |
| 対象 | 架空のリポジトリ `example/monshin`（`tools/monshin-demo.mjs` が手元に作る）。`main` は受付の職員も回答を読める版、`fix/answer-access` は医師だけが読める版 |
| 送ったもの | `monshin.py`（`README.md` は外した）と、架空の説明、ヒアリングの回答。実在の患者・職員の情報はない |
| モデル | `gpt-6.1-terra`（APIが返したモデル名も同じ）。認証はプロキシ（`MUGIURUSHI_AI_AUTH=proxy`） |
| 文書 | mugiurushi-ai の `ingest --all` で取り込んだもの。提供事業者向けガイドライン（経済産業省のPDF）は、この環境からHTTP 403で取り込めていない |
| 実行の方式 | local方式（OSによる隔離なし） |
| 麦漆 | 1〜2回目は `main` の `314a67d` と途中の変更、3回目以降はこのPRの変更 |
| mugiurushi-ai | 1回目は `main` の `6640250`、2回目以降は指示を補った版（Suisan-neki/mugiurushi-ai の同日のPR） |

```sh
cargo build --locked
MUGIURUSHI_AI_DIR=<mugiurushi-ai のチェックアウト> MUGIURUSHI_AI_MODEL=gpt-6.1-terra MUGIURUSHI_AI_AUTH=proxy \
  node tools/monshin-live.mjs
```

スクリプトは画面を操作し、AIの応答・試験の設定・結果・比較を `test-results/monshin-live.json` に、画面の写真を `test-results/monshin-live-*.png` に残す。応答の中身は検査しない。ヒアリングは、決めた語（既定は「有無」「医師だけ」「医師のみ」「表示しない」「読まない」「読めない」）を含む選択肢を選び、合うものがなければ「未定」を選ぶ。

## 結果

| 回 | 説明とヒアリング | `main` の閲覧の試験 | 再試験 |
| --- | --- | --- | --- |
| 1 | 説明は「患者がコマンドで答え、医師が読む」。ヒアリングはスクリプトが最初の選択肢（受付も内容を読める）を選んだ | 試験の設定なし（AIの理由：複数の利用者による読み出しが必要で、単一の読み出しの設定にできない）。未実行 | 満たさない項目がなく、行っていない |
| 2 | 説明に「受付の職員は、回答があるかどうかだけを確かめる」を足した。ヒアリングは「未定」 | 試験の設定あり。満たさない | 照合からやり直した。修正版は満たす。比較は「解消」にならなかった |
| 3〜6 | 2回目と同じ | 4回とも試験の設定あり、満たさない | 了承した試験を引き継いで実行し直した。4回とも「解消」。再試験中のAIへの送信は0回 |

読み込みでは、6回とも「試験環境で動かして確かめます（起動の候補：monshin.py）」になった。照合は20〜27秒、試験の案は17〜33秒、試験の実行は1件で約2秒だった。

AIが作った引数は、2回目以降すべて `monshin.py` の使い方と合っていた（操作は `--dir <.か data> --user P001 answer P001 {{test_value}}`、読み出しは `--dir <同じ> --user reception_b show P001`）。判定条件は「読み出しの出力に `{{test_value}}` を含まない」と、「回答あり」を含む、の組み合わせだった。

### 分かった問題と対処

1. **試験の設定が付かない（1回目）。** AIは、医師・受付・ほかの患者の3人で読み出す試験を考え、1回の読み出しの設定にできないとして設定を作らなかった。指示に、麦漆が1つの試験で動かすのは操作1回と読み出し1回だけであること、要求に反する動きを最も直接に観測できる組み合わせを1つ選び、選ばなかった範囲を注記に書くことを足した（mugiurushi-ai）。注記は試験の案の画面の、実行のしかたの欄に「AIの注記」として示す。
2. **要求と関係の薄い判定条件だけが対応づけられ、「満たす」になった（1回目）。** パスの検証の候補の試験で、判定条件は3つ（保存先に試験の値がある、読み出しが0以外で終わる、読み出しの出力に試験の値を含まない）あったが、候補に対応づけられたのは1つ目だけだった。この試験の読み出し（`show ../answers/P001`）は回答を表示するので、3つ目の条件は満たさないはずだが、合否に使われず「満たす」と表示された。指示に、対応づけるのは要求が守られているかで結果が変わる条件であること、観測の方法をそろえること、終了コードの条件は対応づけられないことを足した。画面では、合否に使わない条件にその旨を添え、了承の前に確かめられるようにした（候補が2つ以上の試験では、条件ごとにどの候補の合否を決めるかも添える）。2回目以降、この形の対応づけは出ていない（5回の実行で観測した範囲）。
3. **ヒアリングの回答が試験の期待に反映される。** 1回目は「受付も内容を読める」と答えたので、受付に表示されることを合格とする案になった。回答は人が選ぶものなので、実装は変えていない。指示には、期待する動作はヒアリングの回答に従うことを明記した。
4. **照合からやり直す再試験では「解消」にならない（2回目）。** 比較は項目を要求の文で対応づけるが、再試験で照合をやり直すと、AIが要求の文を作り直す。`main` は「情報の区分と利用者の職種・担当業務に応じて、利用権限を規定する。」、修正版は「情報の種別・重要性・利用形態に応じて区分し、情報区分ごと、利用者または利用者グループごとの利用権限を規定する。」で、別の項目として並んだ。試験の中身も作り直されるので、同じ試験の実行し直しにもならない。懸念の引き継ぎと同じ考え方で、前のコミットで了承した試験の案を引き継いで実行し直す操作を足した（3回目以降）。

### 前もって進めた記録から続ける流れ

`MONSHIN_DEMO_DIR` を指定して `main` の試験の案の画面まで進めて止め（`MONSHIN_STOP_AT=plan`）、同じ指定で起動し直して続きを実行した。`main` を読み込むと試験の案の画面から始まり、了承・実行（満たさない）・修正用のプロンプト・修正版での実行し直し（解消）まで、AIへの送信0回で進んだ。起動し直すときに、AIへの通信に使うプロキシの指定を届かない宛先に変えた場合も、同じ結果だった。

### モックアップと同じ説明文での結果

本選の動画はモックアップ「照合の流れの画面（Yohaku）」で撮った。その説明文（「架空の診療所の問診システム。患者がスマートフォンで答え、医師が診察室で読む」）で、さらに3回通した。ヒアリングでは3回とも受付の職員の閲覧範囲を聞かれ、スクリプトは「医師のみ」「回答の有無のみ」にあたる選択肢を選んだ。3回とも、受付の閲覧の試験は `main` で満たさない、修正版で「解消」になった。

モックアップと違った点：

- 照合の候補は5〜6件で、試験で確かめられるものは2件（利用権限と、ファイル操作のパスの検証）。モックアップは2件（閲覧の権限と、回答の保存先）。候補の文はガイドラインの言い回しに近い。
- ヒアリングの質問は4〜5件。モックアップは1件。
- パスの検証の候補は、3回のうち2回で、読み出しに `show ../answers/P001` のような患者の指定を使う試験の設定が付き、`main` でも修正版でも満たさなかった（修正版が直すのは受付の閲覧だけ）。このため `main` の結果は「満たさない2件」になることがある。モックアップは「満たさない1件、満たす1件」。
- 根拠の文書は、サイバーセキュリティ対策チェックリストのマニュアルとASVS。モックアップは安全管理ガイドラインと提供事業者ガイドライン。

### モックアップに寄せた後の結果

本人の指示（2026-11-21：「基本は動画に沿う形の実装になってほしい」。実装側が示した案から、確認をヒアリングの画面の中で行う案と、候補の文を具体的にする案を選んだ）を受けて、次の2つを変えた。

- 試験の案を作るときの送る内容の確認を、別の画面からヒアリングの画面の中に移した。画面の並びは、モックアップと同じ「ヒアリング → 試験の案を作っています → 試験の案」になる。
- 照合の指示に、候補の文をこのシステムに当てはめた具体的な一文にすることを足した（mugiurushi-ai）。

モックアップと同じ説明文で、指示を2段階で直しながら通した。

| 指示 | 回数 | 受付の閲覧の試験が `main` で満たさない、修正版で「解消」 |
| --- | --- | --- |
| 具体的な一文にする、だけ | 7回 | 2回。うち4回は、スクリプトが探す語がヒアリングの選択肢の言い回し（「回答の有無だけを確認する」「医師にのみ表示する」）に合わず「未定」を選んだため、人の操作の再現になっていない。残る1回は、利用権限の候補が「文書で確かめる」方法になり、試験の案に入らなかった |
| 上に加えて、規程や権限の定めがシステムの動作に表れる場合は、その動作を書く | 4回 | 4回 |

最後の4回の候補の文は、「問診回答の内容は、職種・担当業務と情報区分に応じた権限がある利用者に表示し、権限がない利用者には表示しない。」のような文になった。試験で確かめられる候補は2〜4件、質問は3〜5件で、件数はモックアップ（候補2件、質問1件）と同じにはなっていない。パスの検証の候補は4回とも試験の設定が付かず、未実行だった。

### 問診アプリの患者の指定を直した後の結果（同日の追記）

上の実行で、`show ../answers/P001` のように患者の指定へ `../` を入れると、保存先を経由して回答を読めることが、麦漆の試験で観測された（パスの検証の候補の試験が `main` でも修正版でも満たさなかった）。これは問診アプリ（`examples/monshin/monshin.py`）に意図せず入っていた不備で、2つの版の違いとして用意したもの（受付の職員が回答の内容を読めるかどうか）ではない。`show` が表示するのを登録されている患者の回答だけにし、登録のない指定は回答がない場合と同じ表示にした。

直した後、モックアップと同じ説明文で4回通した。

| 回 | `main` | 修正版で実行し直した結果 |
| --- | --- | --- |
| 1 | 満たさない1件（受付の閲覧）、未実行2件（パスの検証の試験2件に試験の設定が付かなかった） | 受付の閲覧は「解消」 |
| 2〜4 | 満たさない1件（受付の閲覧）、満たす1件（パスの検証。読み出しは `show ../answers/P001`） | 受付の閲覧は「解消」、パスの検証は満たすのまま |

4回とも、修正版で満たさない項目は残らなかった。

### ヒアリングの質問を絞った後の結果（同日の追記）

照合の指示で、質問を「答えによって、試験で確かめられる候補の期待する結果が変わること」だけに絞らせ、多くとも3件にした（Suisan-neki/mugiurushi-ai#28）。モックアップと同じ説明文で4回通した。

- 質問は、1件が1回、2件が3回だった（それまでは3〜5件）。4回とも、受付の職員の閲覧範囲を聞く質問が含まれた。
- 4回とも、受付の閲覧の試験は `main` で満たさない、修正版で「解消」になった。
- 選択肢に「未定」がない質問が増えた。スクリプトが探す語に合わない質問は、答えないまま進めた。

この4回は、結果の文で試験の値を言葉で示す変更（#254）を入れた麦漆で行った。

## 確認していないこと

- 利用者の手元の環境（macOS）での実行。この記録はクラウドの開発環境（Linux、rootで実行）でのもの。
- ネットワークのない端末での起動。プロキシの宛先を変えて通信を遮った状態は試したが、ネットワークのない端末で `uv run` と麦漆が起動するかは試していない。
- ほかのモデル、ほかの説明文、ほかのヒアリングの回答での結果。説明文に受付の職員の扱いを書かない場合に、閲覧の試験がどうなるかは、1回目の1回しか見ていない。
- パスの検証の候補は、最初の説明文では2回目以降すべて試験の設定が付かず（試験の前に保存先の外へファイルを置く手段がないため）、未実行のまま。
- 指示を足したことで、ほかの対象の試験の案がどう変わるか。
