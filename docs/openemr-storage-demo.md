# 診療データの保存を確かめるデモ

## 目的

開発者の「診療データは意図した場所に正しく保存されるのか」という不安から出発し、AIと検証案を整理する。検証基盤で保存操作と取得できる記録を観測し、確認できたことと残る課題を示す。対象例にはOpenEMRと架空の試験データを使う。

## 動画の流れ

1. **不安を相談する。** 対象のコードと構成を読み込み、「入力した診療記録は想定する保存先に保存されるか」と相談する。AIが参照したコードと、そこからの推測、分からないことを確認する。
2. **検証案を確定する。** 開発者が意図する保存先と確認条件を示す。今回の試験では新規に作るテスト用MariaDBを対象とし、架空の診療記録を保存してDBから読み返す案を確認する。AIの提案と、実行できる試験設定はそれぞれ確認する。
3. **実際の動きを観測する。** OpenEMRの画面で試験用の記録を保存し、操作中のHTTP応答、画面の再表示、指定したDBの読み取り結果、採取できた接続の集計を確認する。待機時間を動画から省略した場合はその旨を示す。
4. **結果と課題を示す。** 指定したテスト用DBで試験値が読み取れたか、各観測の出所とともに示す。取得できなかった記録や確認していない範囲も示し、追加調査や修正の判断につなげる。

患者A・Bの比較や障害注入は、不安や確認したい条件に応じて選ぶ追加の試験である。患者Aの保存によって患者Bの記録が変わらないかを調べる手順は[別の文書](openemr-patient-demo.md)にある。

## 現在できることと残る確認

- OpenEMRの試験は、ブラウザ操作、指定したMariaDBへの読み取り、条件ごとの判定を記録できる。通常時の保存試験と患者A・Bの比較はCIで実行した。
- AIによるコードを参照した確認項目の候補整理は実装されている。録画環境のAI接続と、相談から実行・結果確認までの通しの動作は、別途確認する必要がある。
- 試験用DBから値を読み取れたことは、そのDB内の指定された値についての観測である。本番環境の保存先を確かめたことにはならない。
- 通信記録は採取できた接続の集計であり、特定の保存操作と個々のDB書き込みを対応づけるトレースや、通信内容の記録ではない。集計にない通信が存在しないとは断定できない。
- 参照したソースのコミットと、実行したOpenEMRイメージの中身が一致するかは未確認である。規制への適合、長期保存、認可や監査についてもこの試験だけでは判断できない。

## 収録前の優先事項

1. 収録環境でAIを設定し、相談に対する提案と参照元が表示されるか確認する。つながらない場合は手動で確認項目を登録したと明示し、AIとの通し動作が未確認であることを伝える。
2. 既存の通常時ブラウザ試験を収録環境で実行し、結果画面で試験用DBの読み取りと画面・HTTP・接続の各記録を確認する。過去のCI結果を使用する場合は、その実行であることを明示する。
3. 録画を見直し、「意図した保存先」「実際に読み取った対象」「推測」「未確認」が混ざっていないか確認する。
