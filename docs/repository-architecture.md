# リポジトリからシステム構成を理解する

公開GitHubの固定コミットからREADMEとコードを読み、AIがそのシステム固有の役割と情報の流れを整理する。GitDiagramの構成把握と構造化した図の生成を踏襲する。従来の静的な種類の分類を、利用者向けの構成図の生成には使わない。

## 開発者・運営者がAPIキーを設定する

APIキーはこのサービスの開発者・運営者がサーバーへ設定する。利用者はキー、モデル名、接続先を入力しない。利用者向けの画面とAPIには接続設定の作成・変更機能を設けない。

最初に、開発者の端末で次を実行する。

```bash
cargo run -- ai init
```

`data/app/ai.json`が所有者だけが読み書きできる権限（0600）で作られる。既存のファイルは上書きしない。エディタでこのファイルを開き、`api_key`に作成したキー、`model`に利用するモデル名を記入する。`base_url`はOpenAI互換APIの接続先で、ひな形には `https://api.openai.com/v1` を指定している。モデルはChat CompletionsとJSON応答に対応するものを契約先から選ぶ。キーや利用枠の有効性は、実際の接続で確認する。

```bash
cargo run -- ai test
cargo run
```

`ai test`は設定したモデルへ短い問い合わせを送り、応答の有無を端末に表示する。APIキーや応答の生データは表示しない。接続確認は数十秒以内で終わる。構成図の生成は抜粋を送るため数分かかることがある。生成の待機上限は300秒。上限に達した場合は接続失敗とは別に表示する。接続確認後にサーバーを起動すると、利用者は立場を選び、GitHubのURLを入力して構成図を作れる。

`data/`はGitの管理対象外。キーをソースやチャットへ貼る必要はない。設定はサーバー起動時に読み、変更後は再起動する。保存先を変える場合は `ai init --data-dir DIR`、`ai test --data-dir DIR`、`app DIR` で同じディレクトリを指定する。

配備先の運営者は、既存の `EEL_AI_BASE_URL`、`EEL_AI_MODEL`、`EEL_AI_API_KEY_FILE` による起動時設定も使える。三つをすべて指定した場合はファイルより優先し、一部だけの指定は起動エラーにする。ファイルがなく未設定のときは保存済みの図を開けるが、新しい図の生成やAIへの質問は行わない。

AIへの通信はRustサーバーが担当する。生成と質問にNode.jsは不要。対象がNode.js製の場合の実行には、別途Node.jsが必要。接続や生成の失敗時は理由を表示し、別の図や固定文で補わない。

## 画面で行うこと

リポジトリURLを入力して「構成図を作成する」を押す。READMEとコードの抜粋を設定したAI接続先へ送る。対象コードは起動しない。AIは目的、主な情報の流れ、利用者、画面、業務上の処理、保存先、外部連携を同じ構成モデルへ整理する。

図では、そのシステム固有の役割名と短い説明を表示する。実際のサブシステムのまとまりを枠で表し、役割の種類の分類を配備境界として描かない。非技術者と技術者は同じ要素・接続・配置を参照する。技術者には技術名と実装の詳しい説明を追加する。図全体は表示領域に収め、拡大とスクロールで詳細を読める。

箱や線を選ぶと説明と根拠を確認できる。不安や疑問を入力して「AIと疑問を整理する」を押すと、その図の選んだ部分と関連するコード・設定を基に説明を得る。疑問の整理は一回ごとの質問で、過去の対話を自動で引き継ぐ機能はまだない。AI回答だけでは発言、期待、試験結果を保存しない。記録する内容を自分で確認し、疑問と検証したい動作を保存する。

検証設定と結果は既存の詳細画面で扱う。構成図へ戻ると、疑問を残した図の版と要素・接続を開く。AIが作った構成図を、実行済み・安全確認済みの証拠にしない。

## 読取・生成・検査・保存

`src/system_diagram.rs`が生成と保存、`context.rs`が行番号を保った抜粋、`model.rs`が出力の検査と既存の構成モデルへの変換を担当する。AIの指示は `prompt.txt`、参照元とMIT Licenseは `third_party/gitdiagram` に記載する。

初回の読取に加えて、構成に関係する候補を最大48ファイル補う。AIへ渡す文脈は160KiB以内、ファイル一覧は24KiB以内、本文は最大64ファイル、README等の説明資料は最大6件とする。長いコードの冒頭・中ほど・末尾から分散して抜粋し、実際に渡した行番号を保持する。モデルへ渡さなかった行を根拠として認めない。未読であることから機能が存在しないとは判断しない。

AIは最大34要素、48接続、10グループのJSONを返す。RustがIDの形式・重複、親グループ、接続の両端、実装のパス、説明の上限、根拠の種類と渡した行範囲を検査する。不正な出力には検査結果を返して一度だけ修正を求める。修正後も不正なら図を更新しない。

参照の照合は行が存在することの確認であり、AIの説明や接続方向の正しさの証明ではない。コード、作者の説明、直接の記述が不足する推定を表示で区別する。推定と設定・起動の依存は点線にする。描画する文字列はDOMのテキストとして扱い、モデルのHTMLやJavaScriptを実行しない。ELKはブラウザ内で配置し、外部作図サービスやCDNへモデルを送らない。

成功した図は内容と文脈から求めた版ごとに保存する。通常の再表示は保存した図を使い、AIへ再度問い合わせない。AI設定がない状態でも保存済みの図を開ける。「構成図を作り直す」を明示したときに再生成する。再生成に失敗しても以前の成功した図を残す。保存先全体の保全が必要で、事例だけのバックアップには図や運営者のAI接続設定を含まない。

## API

| 操作 | 用途 |
| --- | --- |
| `GET /api/v1/ai` | 設定の有無・接続先ホスト・モデル名。キーは返さない |
| `POST /api/v1/system-diagram` | `repository`・`commit`から保存済みの図を開くか生成する。`revision`で過去の図、`refresh:true`で再生成 |
| `POST /api/v1/system-diagram/question` | 図の版と部分を指定し、根拠に対応した疑問を整理する |

いずれも既存のlocalhost APIのトークンと送信元の確認を使う。ブラウザからの設定変更・接続確認APIは提供しない。

### AIエージェント（mugiurushi-ai）

運営者が起動時に `EEL_AGENT_URL`（`https://…`、または同じ機械の `http://127.0.0.1:…`。URLとして解析したスキームとホストで判定し、ユーザー情報・クエリ・フラグメントは拒否する）と `EEL_AGENT_TOKEN_FILE`（16文字以上の共有トークンを書いたファイル）を指定すると、画面に「AIに確かめる範囲の案を出してもらう」「AIに結果を説明してもらう」と、確認項目の画面の「ガイドラインとの照合」が出る。未設定・失敗のときは欄を出さないか失敗を示し、確認項目・試験・判定はAIなしで使える。接続先と共有トークンは画面から入力させない。

- 案（`POST /api/v1/agent/propose`）は下書き。人が選んだ案だけを編集中の一覧に加え、既存の「対応づけを保存する」で保存する。既存の部分のIDと判定条件への対応づけはそのまま残り、加えた部分は人が判定条件を選ぶまで未確認。
- 説明（`POST /api/v1/agent/explain`）は、麦漆の状態（判定）とAIによる説明を別の列に示す。
- 送る内容はサーバーが事例から組み立てる（対象のリポジトリ・コミット・パス、実行記録の生ログ・画面写真・試験用の認証情報は含めない）。送る前に、宛先と送る内容そのものを画面に表示し、人が「架空のデータだけ」と確かめたときだけ送る。サーバーは確認した内容の SHA-256 と、送る直前に組み立て直した内容が一致する場合だけ送る。確認項目や自由記入欄に何が書かれているかは麦漆には判断できないため、固定の注意文では安全とみなさない。初回の接続とデモは架空のデータの事例だけで行う。
- 案では、AIが試験で扱わないとした範囲と理由、AIからの質問も表示する。
- ガイドラインとの照合（`POST /api/v1/agent/scan`）は、人が書いたシステムの説明だけを送る（コード・実行記録・ログは自動で送らない）。送る前の確認は案・説明と同じ。候補ごとに出典（文書・ページ・取得元・取得日時・SHA-256・断片の抜粋）と、確かめ方が麦漆の試験の判定条件として観測できる種類か（麦漆の観測の種類の一覧で判定）を示す（観測の種類として判定条件にできることは、その要求をその観測で確かめられることを意味しない）。出典ごとの状態（断片を渡した・渡していない・取り込まれていない）を表に示す。候補は適合・準拠・安全性の判断ではなく、そのままでは確認項目にも判定にも入らない。「この候補をもとに確認項目を書く」は、要求の文を確認項目の入力欄に写すだけで保存しない。人が文を直して保存すると、出所に照合の候補・出典（文書・ページ・SHA-256）・モデル・応答IDが残る。観測の種類と判定条件は、ほかの確認項目と同じく人が選ぶまで未設定。

### ガイドラインの照合から始める流れ（`/flow`）

`/flow` を開き、リポジトリを登録してから5つの段階を順に進める（2026-11-21に画面を組み直した。デザインは本人が承認したモックアップ「照合の流れの画面（Yohaku）」）。1画面に置く主な操作は1つにし、AIエージェントへの送信・読み込み・試験の実行のように待つ処理には、実際に行う処理の段階を上から順に示す画面を出す。段階がすべて終わると「完了しました」を示してから次の画面へ進む。画面の上部には読み込んだリポジトリとブランチを示し、読み込んだ時点のコミットを小さく添える。照合・試験・比較の記録は、そのコミットに固定して残す（ブランチは後から動くため）。記録者の名前は画面で聞かない。保存されていなければ、理解と試験の画面と同じ「開発者（本人確認なし）」を記録に使う。以前の形式のリンク（`/flow?url=…&ref=…`）でも開ける。

1. 照合の準備（4画面）
   - リポジトリの登録：GitHubのリポジトリのURLを入れると、ブランチの一覧を読み（`POST /api/v1/branches`）、ブランチを選ばせる（書かせない）。一覧はGitHubのAPIで読む。GitHubから読めないとき（架空のデモ用のリポジトリ、ネットワークにつながらないとき）は、麦漆が試験用に取得したリポジトリ（データの保存先の `repositories`）にあるブランチを返し、その旨を示す。「読み込む」で、一覧で見たコミットに固定して読み込む。
   - 読み込み中の画面では、ファイルを読み込んだ後に、依存の少ないアプリとして試験環境で動かせるかを、読み取ったコードから判定する（`POST /api/v1/runnable`、`src/runnable.rs`。AIは使わない）。今の版で「動かせる」とするのは、Python 3 の標準ライブラリだけを読み込み、`if __name__ == "__main__"` を持つファイルから起動できるアプリだけ。外部パッケージの読み込み、依存の宣言（`requirements*.txt`、`pyproject.toml` の `dependencies` など）、`docker-compose.yml`、`__main__` がないこと、Pythonのファイルが60件を超えることは「動かせない」理由として示す。試験・例のファイル（`tests/` など）の読み込みは数えない。待ち受けるサーバーとして動く可能性（`http.server` など）は知らせるだけで理由にしない。この判定は推定で、実際に起動できるかは試験の実行で分かる。動かせないアプリは、コードから確かめる（試験は登録するが自動では実行しない）。
   - 照らし合わせないファイルを外す：ファイルは最初からすべて照らし合わせる前提で、外したいファイルにだけ印を付ける。依存の置き場所（`node_modules`・`vendor`）、生成物（`dist`・`build`）、画像などのバイナリ、ロックファイルは最初から外す。秘密の値を持つことが多い種類のファイル（`.env`、鍵ファイルなど、`src/code_tree.rs` の既定の送らないパス）は外したまま戻せない。サーバーも、照合でこの種類のファイルを送る要求を拒否する（`src/agent.rs` の `refuse_secret_files`）。送れる量には上限（40件、1ファイル2万文字まで、合計40万文字）がある。残したファイルが上限を超える場合は「次へ」を押しても進まず、ディレクトリのまとまりを崩さないように1回で送れる量ずつに分けた案を示す。各回の「N回目のファイルだけを残す」で、その回のファイルだけが残る（本人の判断、2026-11-18：「分割試験する旨を提案すれば」）。分けた回の結果をまとめて扱う経路は未実装（#243）。
   - どんなシステムかを書く：システムの説明は任意。
   - AIエージェントに送る内容を確かめる：送信先（AIエージェントのサーバーのアドレスと、その先のモデル）、送るファイル、確かめ方（動かせるかの判定と理由）、説明、大きさを示す。送る内容の全体は折りたたみで読める。payload の SHA-256 は「技術的な詳細」に置く。架空のデータだけであることを確かめる印を付けると「照合を始める」を押せる。サーバーは、画面が添えた SHA-256 と組み立て直した payload が一致した場合だけ送る。その先のモデルは、この画面を開くたびに `GET /api/v1/agent` で問い合わせ、確かめられない場合は理由を示して送らせない。送信が失敗した場合は、送る前の画面に戻ってエラーを示す。画面の構造の記録を照合に添える選択欄は、この画面にはない（`/api/v1/agent/flow-scan` の `screen_evidence` は残っている）。
2. 照合とヒアリング（2画面）
   - 照合の結果：試験で確かめられる候補だけを、ガイドライン別に優先度順で示す。候補ごとに優先度、根拠の文書・ページ、関係するコード、折りたたみの「根拠を読む」を付ける。優先度は該当の見込みと患者の情報に関わるかから決まった規則で付ける。「操作からコードをたどる（任意）」はこの画面の折りたたみにある（照合の前は開いた状態で示す）。対象の操作を書いて「範囲を確かめる」を押すと、送る範囲（リポジトリ、コミット、対象の操作、説明、送らないパスの全体、往復と量の上限）を示す。範囲のSHA-256は「技術的な詳細」に置く。人が了承すると、AIエージェントとの往復で固定したコミットのコードをたどり（`POST /api/v1/agent/investigate`）、懸念ごとに推定、根拠の行、根拠の種類、確かめ方を示す。確かめ方が「麦漆で動かす」の懸念は、照合の候補と一緒に試験の案の候補にする（要求の文は「その懸念が起きていないこと」）。この段は照合の前でも開け、照合をしていない場合は懸念だけから試験の案を作る。前のコミットで試験にした懸念は、新しいコミットへ引き継げる。懸念を出し直すと、前の懸念から作った試験の案・了承・結果は履歴へ移す。
   - ヒアリング：コードだけでは判断できないことを質問として示し、回答は照合し直すときと試験の案に使う。質問が1つのときは、その質問を見出しにする。「人に聞く」の懸念もここに示す。利用者からの質問（折りたたみの「ガイドラインに質問する」）には、取り込んだ文書だけを根拠に出典つきで答える（送る前の確認はダイアログで行う）。「試験の案を作る」を押すと、送る内容の確認の画面（確認候補の件数、ファイル、回答、確かめ方）を経て送る。動かせると判定したアプリでは、試験の設定も求める（`PlanRequest.run`）。麦漆は送る前に動かせるかを自分で判定し直し、動かせるときだけ起動の候補（`run`）を送る内容に入れる。
3. 検証案の了承：「Nつの確認項目を、M件の試験で確かめます。」と件数を示し、試験ごとに手順と合格の条件を示す。折りたたみの「詳細」に、根拠、実行のしかた（コマンド・読み出し・保存先）、判定の条件、確かめる項目ごとの合否の決め方、この試験では確かめない範囲（AIの注記）、観測するもの、関係するコードを示す。合否は候補に対応づけた判定条件だけで決まるので、候補ごとにどの条件で決まるかを示し、どの候補にも対応づけていない条件には「記録するだけで、合否には使いません」と添える（2026-11-21。実際のモデルで、試験の値を保存できたことだけを確かめる条件を候補に対応づけた案が出て、要求に反する読み出しがあっても「満たす」になった。人が了承の前に対応を確かめられるようにした）。AIが試験の設定を作れなかった試験や、コマンドの試験でない試験は「自動では実行しません」と理由を示す。
   - 試験の設定はAIの案に含まれ、麦漆が検査する（`src/agent.rs` の `trial_of`）。起動するファイルは起動の候補のどれか、保存先は作業ディレクトリの中の相対パス、観測の方法は終了コード・標準出力・標準エラー・保存先のファイル・読み出しの出力だけ、終了コードだけでは判定しない、すべての候補をどれかの判定条件に対応づける、を満たさない設定は捨てて理由を示す。候補ごとの対応は、最初の判定条件と同じ観測の方法の条件だけに絞り、その方法を候補の観測の種類にする。使える設定にAIが付けた注記（`trial_note`。1回の操作と1回の読み出しでは確かめない範囲）は、設定と一緒に受け取って画面に示す。
   - 以前は「判定条件への対応づけは人が麦漆で選ぶ。AIの案に含まれていれば受け取らない」としていた。この流れでは、AIが試験の設定と対応を案として出し、人が試験の案の画面で中身を確かめて了承したときだけ使う（本人の判断、2026-11-21：了承後に自動で実行する範囲として「依存の少ないアプリ全般で自動実行」を選んだ。AIの案の対応づけを使うこの扱いは、それを実現するための実装側の提案で、PRで本人が確かめる。確認項目の画面の案（`/api/v1/agent/propose`）は従来どおり対応づけを受け取らない）。
   - 「了承して実行する」（試験の設定がない場合は「了承して登録する」）を押すと、了承した試験ごとに確認項目を作り、照合の候補を確かめる部分として登録する。試験の設定がある試験は、試験の案の判定条件で判定するように設定し、判定条件の内容を添えて対応づけ、固定コミットを取得してから（`/api/v1/prepare`）、既存の試験の設定画面と同じ実行の要求（`/api/v1/execute`）で1件ずつ実行して終わりを待つ。実行はアプリの起動時に選んだ方式で行い、local方式ではOSによる隔離を行わない。途中で失敗しても、登録・実行できた分は残る。登録の途中で止まった場合は試験の案の画面に戻り、やり直すと続きから登録する。試験の設定がない試験は、既存の試験の設定画面で人が設定してから実行する。結果の画面の詳細から設定画面を開くと、了承した案が出る。
4. 結果：満たさない・満たす・未確認・未実行の件数を示し、項目ごとに状態と、試行で記録した判定条件ごとの結果（麦漆の説明の文）を示す。状態は確認項目の観測の状態（事例の記録が正）だけで決める。実行していない試験は「未実行」とし、成功・失敗として数えない。実行したが判定できなかった部分は「未確認」とし、判定条件ごとの理由（読み出しのプロセスが正常に終わっていない、など）を示す。詳細には、根拠（懸念の項目は懸念・推定・根拠の行）、試験と手順、合格の条件と観測、記録、試験の設定と記録へのリンクを示す。照合したコミットと違う版の試験の結果は「別の版の試験」とし、このコミットの結果として数えない。試験にしていない候補は、合否を付けずに折りたたみで示す。
5. 修正用のプロンプト：満たさなかった項目のプロンプトを作る。ガイドラインの該当箇所、合格の条件、判定条件ごとの観測の結果（満たす・満たさないの区別だけ）、試行の記録、関係しそうなコード、対象のブランチとコミットを入れる。試験に使った値、認証情報、生のログは入れない。懸念の項目は、ガイドラインの代わりに懸念・コードからの推定・根拠の行を入れる。「再試験へ」で、修正したブランチを一覧から選ぶ。今の記録に了承済みの試験と結果があれば（懸念から作った案を除く）、主な操作は「了承した試験を、このブランチで実行し直す」になる。この操作は、選んだブランチを読み込み、保存日時がいちばん新しい前のコミットの記録から、照合・回答・了承した試験の案を今のコミットの記録に写す（`ui/flow-record.js` の `carryablePlan`・`carriedPlan`）。照合と試験の案はAIへ送らない。了承と結果は写さず、試験の案の画面で人が確かめて了承し直してから実行する。写した照合と案には引き継ぎ元のコミットを残し、照合の画面と試験の案の画面に「前のコミットのコードから作ったもので、今のコミットのコードはAIと照合していない」と示す。確認項目の出どころにも引き継ぎ元を書く。起動するファイルが今のコミットの起動の候補にない試験は、試験の設定を外して理由を示す。読み込んだコミットにすでに照合か案の記録があれば、それを残して引き継がない。「照合からやり直す」を選ぶと、これまでどおり同じ流れを照合からやり直す。結果の控えを、保存日時がいちばん新しい前のコミットの記録と比べ、「解消」「変わらず満たさない」「新たに満たさない」を示す。項目は要求の文で対応づける。照合からやり直すと、AIが要求の文を作り直すので、同じ項目でも文が変わって比べられないことがある（2026-11-21に実際のモデルで確かめた。[記録](validation-monshin-live-2026-11-21.md)）。試験を引き継ぐ操作は、このための実装側の提案で、PRで本人が確かめる。修正したコードそのものの照合は行わないので、修正で新しく生じた不足は、照合からやり直さないと見つからない。

架空の問診アプリ（`examples/monshin`）と `tools/monshin-demo.mjs` で、架空のリポジトリ `example/monshin`（ブランチ `main` と `fix/answer-access`）を手元に作り、画面からこの流れを通せる。`MONSHIN_DEMO_DIR` にディレクトリを指定すると、架空のリポジトリとデータの保存先をそこに作って止めても消さず、同じ指定で起動し直すと続きから使う（コミットが変わらないので、照合・試験の案・結果の記録が残り、読み込むと進めたところの画面から始まる）。指定しなければ、これまでどおり一時ディレクトリに作り、止めると消す。`tools/flow-auto-smoke.mjs` は、AIエージェントの応答だけを偽物に差し替え、ブランチの一覧・読み込み・動かせるかの判定・試験の実行・判定を本物で通す。`tools/monshin-live.mjs` は、同じ流れを実際の mugiurushi-ai と実際のモデルで画面から通し、応答と結果を `test-results/monshin-live.json` に記録する（応答の中身は検査しない）。
